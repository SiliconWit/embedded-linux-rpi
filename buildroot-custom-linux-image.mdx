A sensor node built on the standard Raspberry Pi OS image carries hundreds of programs it will never use: a desktop, office tools, games, and background services. Each one uses memory, slows the start, and is one more thing that can fail or be attacked. For a device with one job, you want an image that holds only what the job needs. Buildroot is a build system: a set of scripts that reads one configuration file, compiles everything from source code, and produces a complete Linux image with exactly the packages you select. In this lesson you configure Buildroot for the Raspberry Pi Zero 2 W, add the BME280 sensor reader as your own package, add your own configuration files, and produce an image that you write to an SD card. The image starts your application at boot, with almost nothing else running. #Buildroot #MinimalLinux #EmbeddedSystems

## What We Are Building

<Card title="Minimal Buildroot Image with Sensor Application" icon="star">
A Linux image with under 32 MB of files that starts the Raspberry Pi Zero 2 W and runs a sensor monitoring application. The image contains a kernel you compiled, BusyBox (one small program that provides the shell and the common commands), your BME280 sensor reader as a Buildroot package, and a short script that starts the application at boot. There is no package manager, no desktop, and no service you did not choose.
</Card>

**Image specifications:**

| Parameter | Value |
|-----------|-------|
| Target | Raspberry Pi Zero 2 W (AArch64) |
| Kernel | Custom-configured (as in the kernel configuration lesson) |
| Init system | BusyBox init |
| Root filesystem | ext4, read-only, with RAM storage for runtime data |
| Image size | Under 32 MB used in the root filesystem (the SD card image file is about 97 MB with the partition sizes below) |
| Packages | busybox, sensor-monitor (yours), i2c-tools, dropbear (optional SSH) |
| Build time | 20 to 40 minutes on a modern x86_64 host |

## What is Buildroot?

<InArticleAd />


On a microcontroller you compile one program and write it to flash memory. A Linux device needs three parts on its card, and they must agree with each other:

- The **bootloader** is the small program that runs first and loads the kernel.
- The **kernel** is Linux itself. It manages memory, processes and hardware.
- The **root filesystem** is the tree of folders and files that the kernel mounts as `/`: the shell, the libraries, the configuration files and your application.

A program compiled against one version of the C library fails on a root filesystem that holds another. And if you take a ready image and delete things by hand, you cannot repeat the work exactly on the next device.

Buildroot builds every part from source in one run. It first builds a cross-compilation toolchain (a compiler that runs on your PC and produces code for the ARM processor of the Pi). With that one compiler it builds the kernel and every package, then packs the result into one image file. The same configuration file gives the same image every time.

```text
  make menuconfig
    │
    ▼
  .config (target arch, packages, kernel)
    │
    ▼
  make
    ├──► Download sources ──► /dl/
    ├──► Build toolchain  ──► /host/
    ├──► Build kernel     ──► Image.gz
    ├──► Build BusyBox    ──► rootfs utils
    ├──► Build packages   ──► your app
    └──► Generate image   ──► sdcard.img
                               │
                               ▼
                          dd to microSD
```

Yocto, the build system of a later lesson, does the same job with more machinery: a first build of 1 to 3 hours against 20 to 40 minutes, and about 10,000 packages against 2,800. Buildroot is simpler to learn and suits a device with one purpose. It suits a family of products with several hardware variants less well.

Everything Buildroot produces goes into the `output/` folder. Two of its folders are work areas:

```text
  output/
  ├── build/           Extracted + compiled
  │   ├── busybox-*/   sources for each
  │   ├── linux-*/     selected package
  │   └── sensor-monitor-*/
  └── host/            Cross-toolchain +
      └── bin/         build tools (runs
          └── aarch64- on your x86 PC)
              linux-gnu-gcc
```

The other two hold the result. You can inspect `target/` before it is packed into the files in `images/`.

```text
  output/
  ├── images/          Final output
  │   ├── Image.gz     Kernel
  │   ├── rootfs.ext4  Root filesystem
  │   └── sdcard.img   Flashable image
  └── target/          Staging rootfs
      ├── bin/         (becomes / on target)
      ├── etc/
      └── usr/
```

## Downloading and Initial Configuration

<InArticleAd />


<Steps>

1. **Clone Buildroot**

   ```bash
   cd ~
   git clone https://git.buildroot.net/buildroot
   cd buildroot
   git checkout 2024.02  # Use a stable release tag
   ```

2. **Load the default configuration for Raspberry Pi Zero 2 W**

   Buildroot has thousands of settings, and nobody sets them all by hand. It ships a defconfig (a short file of known-good settings) for many boards. The Pi Zero 2 W uses the AArch64 (64-bit ARM) one. Run `make list-defconfigs | grep raspberrypi` to see the exact names in your release:

   ```bash
   make raspberrypizero2w_64_defconfig
   ```

   This creates a `.config` file with working defaults: AArch64 target, internal toolchain, Linux kernel from the Raspberry Pi fork, and a minimal root filesystem.

3. **Open the configuration menu**

   ```bash
   make menuconfig
   ```

   The menu has one section for each part of the image. The next part of the lesson goes through the sections you change.

</Steps>

## Adding Standard Packages

<InArticleAd />


A package is one piece of software that Buildroot knows how to download, compile and install. You select packages under `Target packages` in menuconfig. Each one has a `BR2_PACKAGE_*` variable in Kconfig (the menu language that Buildroot shares with the Linux kernel). Some packages select the libraries they need.

Add I2C tools for debugging sensor communication:

```
Target packages --->
    Hardware handling --->
        [*] i2c-tools
```

Add Dropbear for lightweight SSH access during development:

```
Target packages --->
    Networking applications --->
        [*] dropbear
```

You can also enable packages directly in the config file:

```bash
# Append to .config (or use menuconfig)
echo "BR2_PACKAGE_I2C_TOOLS=y" >> .config
echo "BR2_PACKAGE_DROPBEAR=y" >> .config
make olddefconfig  # Resolve dependencies
```

`make olddefconfig` applies the new settings and resolves any dependencies (for example, Dropbear requires the `zlib` library, which will be selected automatically).

## Creating a Custom Package

<InArticleAd />


Your own program is not in Buildroot's list. If you copied a compiled file into the image by hand, the next clean build would lose it, so you make it a package. A package needs two small files with fixed names: `Config.in` puts it in the menu, and a `.mk` file (the recipe) says how to build and install it.

<FileTree>
- buildroot/
  - package/
    - sensor-monitor/
      - Config.in
      - sensor-monitor.mk
      - src/
        - sensor-monitor.c
        - Makefile
</FileTree>

<Steps>

1. **Create the package directory**

   ```bash
   mkdir -p package/sensor-monitor/src
   ```

2. **Write Config.in**

   This file defines the package in Buildroot's Kconfig system:

   ```bash title="package/sensor-monitor/Config.in"
   config BR2_PACKAGE_SENSOR_MONITOR
       bool "sensor-monitor"
       help
         BME280 sensor monitoring application.
         Reads temperature, humidity, and pressure via I2C
         and logs to stdout or a file.
   ```

3. **Write the Buildroot package recipe**

   The `.mk` file tells Buildroot how to fetch, build, and install your package:

   ```makefile title="package/sensor-monitor/sensor-monitor.mk"
   ################################################################################
   #
   # sensor-monitor
   #
   ################################################################################

   SENSOR_MONITOR_VERSION = 1.0
   SENSOR_MONITOR_SITE = $(SENSOR_MONITOR_PKGDIR)/src
   SENSOR_MONITOR_SITE_METHOD = local
   SENSOR_MONITOR_LICENSE = MIT

   define SENSOR_MONITOR_BUILD_CMDS
   	$(TARGET_MAKE_ENV) $(MAKE) $(TARGET_CONFIGURE_OPTS) \
   		-C $(@D) all
   endef

   define SENSOR_MONITOR_INSTALL_TARGET_CMDS
   	$(INSTALL) -D -m 0755 $(@D)/sensor-monitor \
   		$(TARGET_DIR)/usr/bin/sensor-monitor
   endef

   $(eval $(generic-package))
   ```

   Key points about this recipe:
   - `SENSOR_MONITOR_SITE_METHOD = local` means the source is in the Buildroot tree (not fetched from the internet).
   - `SENSOR_MONITOR_SITE` points to the `src/` directory.
   - `TARGET_MAKE_ENV` and `TARGET_CONFIGURE_OPTS` pass the cross-compiler and its flags to your Makefile. Without them the program is compiled for your PC and cannot run on the Pi.
   - `$(eval $(generic-package))` registers this as a Buildroot package.

4. **Write the application source**

   Most of the listing is the datasheet arithmetic that turns the raw numbers of the BME280 into °C, hPa and percent. Read `main()` at the end first. It opens the I2C bus, checks the chip ID, reads the calibration, then prints one CSV line every `interval_sec` seconds. The interval is the first command-line argument.

   ```c title="package/sensor-monitor/src/sensor-monitor.c"
   #include <stdio.h>
   #include <stdlib.h>
   #include <fcntl.h>
   #include <unistd.h>
   #include <sys/ioctl.h>
   #include <linux/i2c-dev.h>
   #include <stdint.h>
   #include <time.h>
   #include <signal.h>

   #define BME280_ADDR      0x76
   #define BME280_CHIP_ID   0x60
   #define BME280_REG_ID    0xD0
   #define BME280_REG_CTRL_HUM   0xF2
   #define BME280_REG_CTRL_MEAS  0xF4
   #define BME280_REG_CONFIG     0xF5
   #define BME280_REG_DATA       0xF7
   #define BME280_REG_CALIB00    0x88
   #define BME280_REG_CALIB26    0xE1

   static volatile int running = 1;

   static void signal_handler(int sig)
   {
       (void)sig;
       running = 0;
   }

   static int i2c_write_byte(int fd, uint8_t reg, uint8_t val)
   {
       uint8_t buf[2] = { reg, val };
       if (write(fd, buf, 2) != 2)
           return -1;
       return 0;
   }

   static int i2c_read_bytes(int fd, uint8_t reg, uint8_t *buf, int len)
   {
       if (write(fd, &reg, 1) != 1)
           return -1;
       if (read(fd, buf, len) != len)
           return -1;
       return 0;
   }

   /* BME280 compensation formulas (from datasheet) */
   struct bme280_calib {
       uint16_t dig_T1;
       int16_t  dig_T2, dig_T3;
       uint16_t dig_P1;
       int16_t  dig_P2, dig_P3, dig_P4, dig_P5;
       int16_t  dig_P6, dig_P7, dig_P8, dig_P9;
       uint8_t  dig_H1, dig_H3;
       int16_t  dig_H2, dig_H4, dig_H5;
       int8_t   dig_H6;
   };

   static int read_calibration(int fd, struct bme280_calib *cal)
   {
       uint8_t buf[26];
       uint8_t buf2[7];

       if (i2c_read_bytes(fd, BME280_REG_CALIB00, buf, 26) < 0)
           return -1;

       cal->dig_T1 = (uint16_t)(buf[1] << 8 | buf[0]);
       cal->dig_T2 = (int16_t)(buf[3] << 8 | buf[2]);
       cal->dig_T3 = (int16_t)(buf[5] << 8 | buf[4]);
       cal->dig_P1 = (uint16_t)(buf[7] << 8 | buf[6]);
       cal->dig_P2 = (int16_t)(buf[9] << 8 | buf[8]);
       cal->dig_P3 = (int16_t)(buf[11] << 8 | buf[10]);
       cal->dig_P4 = (int16_t)(buf[13] << 8 | buf[12]);
       cal->dig_P5 = (int16_t)(buf[15] << 8 | buf[14]);
       cal->dig_P6 = (int16_t)(buf[17] << 8 | buf[16]);
       cal->dig_P7 = (int16_t)(buf[19] << 8 | buf[18]);
       cal->dig_P8 = (int16_t)(buf[21] << 8 | buf[20]);
       cal->dig_P9 = (int16_t)(buf[23] << 8 | buf[22]);

       cal->dig_H1 = buf[25];

       if (i2c_read_bytes(fd, BME280_REG_CALIB26, buf2, 7) < 0)
           return -1;

       cal->dig_H2 = (int16_t)(buf2[1] << 8 | buf2[0]);
       cal->dig_H3 = buf2[2];
       cal->dig_H4 = (int16_t)((buf2[3] << 4) | (buf2[4] & 0x0F));
       cal->dig_H5 = (int16_t)((buf2[5] << 4) | (buf2[4] >> 4));
       cal->dig_H6 = (int8_t)buf2[6];

       return 0;
   }

   static int32_t t_fine;

   static double compensate_temperature(int32_t adc_T, struct bme280_calib *cal)
   {
       double var1, var2, T;
       var1 = ((double)adc_T / 16384.0 - (double)cal->dig_T1 / 1024.0)
              * (double)cal->dig_T2;
       var2 = (((double)adc_T / 131072.0 - (double)cal->dig_T1 / 8192.0)
              * ((double)adc_T / 131072.0 - (double)cal->dig_T1 / 8192.0))
              * (double)cal->dig_T3;
       t_fine = (int32_t)(var1 + var2);
       T = (var1 + var2) / 5120.0;
       return T;
   }

   static double compensate_pressure(int32_t adc_P, struct bme280_calib *cal)
   {
       double var1, var2, p;
       var1 = ((double)t_fine / 2.0) - 64000.0;
       var2 = var1 * var1 * (double)cal->dig_P6 / 32768.0;
       var2 = var2 + var1 * (double)cal->dig_P5 * 2.0;
       var2 = (var2 / 4.0) + ((double)cal->dig_P4 * 65536.0);
       var1 = ((double)cal->dig_P3 * var1 * var1 / 524288.0
              + (double)cal->dig_P2 * var1) / 524288.0;
       var1 = (1.0 + var1 / 32768.0) * (double)cal->dig_P1;
       if (var1 == 0.0)
           return 0;
       p = 1048576.0 - (double)adc_P;
       p = (p - (var2 / 4096.0)) * 6250.0 / var1;
       var1 = (double)cal->dig_P9 * p * p / 2147483648.0;
       var2 = p * (double)cal->dig_P8 / 32768.0;
       p = p + (var1 + var2 + (double)cal->dig_P7) / 16.0;
       return p / 100.0;  /* hPa */
   }

   static double compensate_humidity(int32_t adc_H, struct bme280_calib *cal)
   {
       double h;
       h = ((double)t_fine) - 76800.0;
       if (h == 0.0)
           return 0;
       h = (adc_H - ((double)cal->dig_H4 * 64.0
           + ((double)cal->dig_H5 / 16384.0) * h))
           * ((double)cal->dig_H2 / 65536.0
           * (1.0 + (double)cal->dig_H6 / 67108864.0 * h
           * (1.0 + (double)cal->dig_H3 / 67108864.0 * h)));
       h = h * (1.0 - (double)cal->dig_H1 * h / 524288.0);
       if (h > 100.0) h = 100.0;
       if (h < 0.0) h = 0.0;
       return h;
   }

   int main(int argc, char *argv[])
   {
       const char *i2c_dev = "/dev/i2c-1";
       int interval_sec = 5;
       int fd;
       uint8_t chip_id;
       struct bme280_calib cal;
       uint8_t data[8];
       int32_t adc_T, adc_P, adc_H;

       if (argc > 1)
           interval_sec = atoi(argv[1]);
       if (interval_sec < 1)
           interval_sec = 1;

       signal(SIGINT, signal_handler);
       signal(SIGTERM, signal_handler);

       fd = open(i2c_dev, O_RDWR);
       if (fd < 0) {
           perror("open i2c");
           return 1;
       }

       if (ioctl(fd, 0x0703 /* I2C_SLAVE */, BME280_ADDR) < 0) {
           perror("ioctl I2C_SLAVE");
           close(fd);
           return 1;
       }

       /* Verify chip ID */
       if (i2c_read_bytes(fd, BME280_REG_ID, &chip_id, 1) < 0) {
           fprintf(stderr, "Failed to read chip ID\n");
           close(fd);
           return 1;
       }
       if (chip_id != BME280_CHIP_ID) {
           fprintf(stderr, "Unexpected chip ID: 0x%02X\n", chip_id);
           close(fd);
           return 1;
       }

       /* Read calibration data */
       if (read_calibration(fd, &cal) < 0) {
           fprintf(stderr, "Failed to read calibration\n");
           close(fd);
           return 1;
       }

       /* Configure: 1x oversampling for all, normal mode */
       i2c_write_byte(fd, BME280_REG_CTRL_HUM, 0x01);
       i2c_write_byte(fd, BME280_REG_CONFIG, 0xA0);   /* 1000ms standby */
       i2c_write_byte(fd, BME280_REG_CTRL_MEAS, 0x27); /* T:1x, P:1x, normal */

       printf("timestamp,temperature_c,pressure_hpa,humidity_pct\n");

       while (running) {
           sleep(interval_sec);

           if (i2c_read_bytes(fd, BME280_REG_DATA, data, 8) < 0) {
               fprintf(stderr, "Read error\n");
               continue;
           }

           adc_P = (int32_t)((data[0] << 12) | (data[1] << 4) | (data[2] >> 4));
           adc_T = (int32_t)((data[3] << 12) | (data[4] << 4) | (data[5] >> 4));
           adc_H = (int32_t)((data[6] << 8) | data[7]);

           double temp = compensate_temperature(adc_T, &cal);
           double pres = compensate_pressure(adc_P, &cal);
           double hum  = compensate_humidity(adc_H, &cal);

           time_t now = time(NULL);
           printf("%ld,%.2f,%.2f,%.2f\n", (long)now, temp, pres, hum);
           fflush(stdout);
       }

       close(fd);
       printf("Shutting down.\n");
       return 0;
   }
   ```

5. **Write the application Makefile**

   ```makefile title="package/sensor-monitor/src/Makefile"
   CC ?= gcc
   CFLAGS ?= -Wall -O2

   all: sensor-monitor

   sensor-monitor: sensor-monitor.c
   	$(CC) $(CFLAGS) $(LDFLAGS) -o $@ $< -lm

   clean:
   	rm -f sensor-monitor
   ```

6. **Register the package with Buildroot**

   Add your package to Buildroot's package Config.in so menuconfig can find it. The file is one big `menu "Target packages"` block that closes with `endmenu` on its last lines, so do not append to the end of the file: a line after that `endmenu` lands outside the menu. Open `package/Config.in` in an editor and add this line inside the block, for example just above its final `endmenu`:

   ```bash
   source "package/sensor-monitor/Config.in"
   ```

   Check that it is there:

   ```bash
   grep -n "sensor-monitor" package/Config.in
   ```

   Then enable it:

   ```bash
   make menuconfig
   # Navigate to: Target packages --> sensor-monitor
   # Enable it with [*]
   ```

   Or directly:

   ```bash
   echo "BR2_PACKAGE_SENSOR_MONITOR=y" >> .config
   make olddefconfig
   ```

</Steps>

## Filesystem Overlays

<InArticleAd />


Packages give you programs, but not your own settings and start scripts. If you edited those in `output/target/`, the next clean build would erase them. A filesystem overlay is a folder tree that Buildroot copies on top of the root filesystem as the last step. A file at `etc/inittab` in the overlay becomes `/etc/inittab` in the image. Like a sticker placed over a printed form, your file covers the one a package put at the same path.

Create the overlay directory structure:

```bash
mkdir -p board/siliconwit/rpi0w2/rootfs_overlay/etc/init.d
mkdir -p board/siliconwit/rpi0w2/rootfs_overlay/etc/sensor-monitor
```

<FileTree>
- board/
  - siliconwit/
    - rpi0w2/
      - rootfs_overlay/
        - etc/
          - inittab
          - init.d/
            - S99sensor
          - sensor-monitor/
            - config.conf
</FileTree>

**Custom inittab** (controls what BusyBox init starts at boot). The `sysinit` lines run once at boot, in order. A `respawn` line is started again each time its program ends. The line to notice is `rcS`: it runs every script in `/etc/init.d/` whose name starts with `S`, in number order.

```bash title="board/siliconwit/rpi0w2/rootfs_overlay/etc/inittab"
# System initialization
::sysinit:/bin/mount -t proc proc /proc
::sysinit:/bin/mount -o remount,rw /
::sysinit:/bin/mkdir -p /dev/pts /dev/shm
::sysinit:/bin/mount -a
::sysinit:/sbin/swapon -a
null::sysinit:/bin/ln -sf /proc/self/fd /dev/fd
null::sysinit:/bin/ln -sf /proc/self/fd/0 /dev/stdin
null::sysinit:/bin/ln -sf /proc/self/fd/1 /dev/stdout
null::sysinit:/bin/ln -sf /proc/self/fd/2 /dev/stderr
::sysinit:/bin/hostname -F /etc/hostname

# Run all startup scripts
::sysinit:/etc/init.d/rcS

# Serial console
ttyAMA0::respawn:/sbin/getty -L ttyAMA0 115200 vt100

# Graceful shutdown
::shutdown:/etc/init.d/rcK
::shutdown:/sbin/swapoff -a
::shutdown:/bin/umount -a -r
```

**Init script for the sensor application.** The name `S99sensor` makes it one of the last to run. It starts the program in the background, sends its output to the CSV log, and saves its process number in a PID file so that `stop` can find it. Notice what is missing: if the program crashes, nothing starts it again.

```bash title="board/siliconwit/rpi0w2/rootfs_overlay/etc/init.d/S99sensor"
#!/bin/sh

DAEMON=/usr/bin/sensor-monitor
PIDFILE=/var/run/sensor-monitor.pid
LOGFILE=/var/log/sensor-monitor.csv
INTERVAL=10

case "$1" in
    start)
        printf "Starting sensor-monitor: "
        # -b sends the daemon's output to /dev/null, so the redirection
        # to the log file must happen inside the background process
        start-stop-daemon -S -b -m -p "$PIDFILE" \
            -x /bin/sh -- -c "exec $DAEMON $INTERVAL > $LOGFILE 2>&1"
        echo "OK"
        ;;
    stop)
        printf "Stopping sensor-monitor: "
        start-stop-daemon -K -p "$PIDFILE"
        rm -f "$PIDFILE"
        echo "OK"
        ;;
    restart)
        $0 stop
        sleep 1
        $0 start
        ;;
    *)
        echo "Usage: $0 {start|stop|restart}"
        exit 1
        ;;
esac
```

Make the init script executable:

```bash
chmod +x board/siliconwit/rpi0w2/rootfs_overlay/etc/init.d/S99sensor
```

**Application configuration:**

```ini title="board/siliconwit/rpi0w2/rootfs_overlay/etc/sensor-monitor/config.conf"
# Sensor monitor configuration
i2c_bus=/dev/i2c-1
interval_seconds=10
log_file=/var/log/sensor-monitor.csv
```

This version of the program takes its interval from the command line in `S99sensor` and does not read `config.conf` yet. The file shows where an application's settings belong in an overlay.

The overlay path must match what you set in `System configuration --> Root filesystem overlay directories`.

## Building the Image

<InArticleAd />


With everything configured, build the complete image:

```bash
make 2>&1 | tee build.log
```

The build goes through the stages of the drawing above. The toolchain (5 to 10 minutes) and the kernel (5 to 15 minutes) take most of the time, the packages 2 to 5 minutes, and the two image steps under a minute each. The first build takes 20 to 40 minutes on a modern 8-core PC. Parallel jobs make it faster:

```bash
make -j$(nproc) 2>&1 | tee build.log
```

After the build completes, the output images are in `output/images/`:

```bash
ls -lh output/images/
```

Expected output:

```
-rw-r--r-- 1 user user   32M  boot.vfat
-rw-r--r-- 1 user user   18M  Image
-rw-r--r-- 1 user user   15K  bcm2710-rpi-zero-2-w.dtb
-rw-r--r-- 1 user user   64M  rootfs.ext4
-rw-r--r-- 1 user user   97M  sdcard.img
```

The `sdcard.img` file is the complete image for the card. The `rootfs.ext4` file is the root partition alone: its 64 MB is the partition size you set, not the size of the files in it.

## Read-Only Root Filesystem

<InArticleAd />


A field device loses power without warning. If the card is in the middle of a write at that moment, the filesystem can be damaged and the device may not start again. SD cards also wear out from repeated writes. A root filesystem mounted read-only has neither problem.

Configure Buildroot for a read-only root by turning this option off:

```
System configuration --->
    [ ] remount root filesystem read-write during boot
```

Because the overlay supplies its own `/etc/inittab`, also delete the `::sysinit:/bin/mount -o remount,rw /` line from that file. Otherwise it remounts the root filesystem read-write on every boot.

Programs still need somewhere to write logs and PID files. A tmpfs is a filesystem that lives in RAM. Add tmpfs mounts in your overlay's `/etc/fstab`, the table of what is mounted where:

```bash title="board/siliconwit/rpi0w2/rootfs_overlay/etc/fstab"
# <device>     <mount>   <type>  <options>         <dump> <pass>
/dev/mmcblk0p1 /boot     vfat    ro                0      0
/dev/mmcblk0p2 /         ext4    ro,noatime        0      1
tmpfs          /tmp      tmpfs   nosuid,nodev      0      0
tmpfs          /var/log  tmpfs   nosuid,nodev      0      0
tmpfs          /var/run  tmpfs   nosuid,nodev      0      0
```

With this setup:

- The root filesystem (`/`) and boot partition (`/boot`) are mounted read-only.
- `/tmp`, `/var/log`, and `/var/run` are in RAM. Data written here is lost on reboot. That includes the sensor CSV log in `/var/log`.
- The SD card receives no writes during normal operation, so it lasts much longer.
- If power is cut at any point, the filesystem is still consistent, because nothing was being written to it.

If the readings must survive a reboot, add a small writable data partition on the SD card, or use an external storage device.

## Rebuilding and Iterating

<InArticleAd />


You do not rebuild everything when you change one package. Buildroot does not notice that you edited a source file, so you tell it which package to build again.

**Rebuild a single package:**

```bash
# Rebuild only the sensor-monitor package
make sensor-monitor-rebuild

# Then regenerate the filesystem image
make
```

**Rebuild the kernel (after changing kernel config):**

```bash
make linux-menuconfig   # Modify kernel config
make linux-rebuild      # Rebuild just the kernel
make                    # Regenerate images
```

**Full clean rebuild (when changing toolchain or major config):**

```bash
make clean
make -j$(nproc)
```

**Save your configuration:**

```bash
# Save Buildroot config to a defconfig file
make savedefconfig BR2_DEFCONFIG=configs/siliconwit_rpi0w2_defconfig
```

This creates a short defconfig to keep in version control: with it, anyone can build the same image. To restore it later:

```bash
make siliconwit_rpi0w2_defconfig
```

**Other useful make targets:**

| Command | Purpose |
|---------|---------|
| `make sensor-monitor-dirclean` | Delete package build directory entirely |
