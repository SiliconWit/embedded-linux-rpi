On a microcontroller, your program is the only software on the chip. On a Linux board, your program is the last link of a chain: firmware starts the board, a kernel takes control of the hardware, a set of files is found on the card, and only then your code runs. When one link is missing the board does not start, and a ready-made system image gives you no way to find which one. In this lesson you build every link by hand for a Raspberry Pi Zero 2 W. You compile a C program on your PC for the board's ARM processor (this is cross-compilation), prepare a microSD card with the firmware, a kernel and a minimal root filesystem, and watch "Hello from custom Linux!" arrive on a serial console at first boot. #EmbeddedLinux #CrossCompilation #BootProcess

## The Linux Boot Sequence

<InArticleAd />


A microcontroller starts your program at once, because the program sits in flash at a fixed address. A Linux board cannot do that. At power-on its RAM is not yet set up, and the kernel is an ordinary file on an SD card. So the board starts in stages, and each stage does only enough to load the next one:

- **Firmware (the bootloader)**: small code that sets up the RAM, reads the card and copies the kernel into memory.
- **Kernel**: the program that controls the hardware and shares the processor and the memory among all other programs. It contains the drivers.
- **Root filesystem**: the directory tree the kernel mounts as `/`. It holds every program and setting. The kernel alone contains no shell and no commands.
- **Init**: the first program the kernel starts from the root filesystem. It starts all others. With no init, the kernel stops with a panic.

The stages work like a relay race: each runner carries the baton only to the next runner, and when one runner is missing, the race stops at that point. A boot stops in the same way, at the first stage whose file is missing or wrong. (In a race each runner stops after the hand-over; here the kernel keeps running under every program.)

On this board the first two stages run on the graphics processor (GPU):

```text
  Stages 1 and 2: the GPU loads the kernel
  ─────────────────────────────────────────
  ┌─────────────────┐
  │ GPU ROM         │ Runs at power-on
  │ (in the chip)   │ Cannot be changed
  │ loads           │ Reads the FAT32
  │ bootcode.bin    │ boot partition
  └────────┬────────┘
           │ bootcode.bin loads start.elf
           ▼
  ┌─────────────────┐
  │ start.elf       │ Sets up the RAM
  │ reads           │ Loads the kernel and
  │ config.txt      │ the device tree file
  └─────────────────┘
```

Then the ARM processor starts, and Linux takes over:

```text
  Stages 3 and 4: Linux runs on the ARM cores
  ─────────────────────────────────────────
  ┌─────────────────┐
  │ Linux kernel    │ Starts the 4 cores
  │ reads           │ Finds the hardware
  │ cmdline.txt     │ Mounts the rootfs
  └────────┬────────┘
           ▼
  ┌─────────────────┐
  │ /sbin/init      │ Process number 1
  │ (BusyBox or     │ Runs the start script
  │  systemd)       │ Opens a shell
  └─────────────────┘
```

The board's chip, the Broadcom BCM2710A1, is a system on chip (SoC): it holds a VideoCore IV GPU and four ARM Cortex-A53 processor cores. The GPU runs first. The ARM cores stay in reset until the GPU firmware releases them.

<Steps>
1. **GPU ROM bootloader (first stage)**

   When power is applied, the VideoCore IV GPU starts executing code from a small ROM embedded in the SoC. This ROM is burned into silicon at the factory and cannot be modified. Its only job is to look for the file `bootcode.bin` on the first FAT32 partition of the SD card. `bootcode.bin` is a small second-stage loader that then loads `start.elf` (only the Pi 4 and later, which boot from an EEPROM, work without `bootcode.bin`). If the SD card is missing or the file is not found, the boot stops here and the green LED gives an error blink pattern.

2. **`start.elf` and `config.txt` (second stage)**

   The GPU loads `start.elf`, which is the main firmware blob. This file initializes SDRAM, reads `config.txt` to determine hardware configuration (clock speeds, UART, display, GPU memory split), and loads the Linux kernel image into memory. On a 64-bit setup, `start.elf` reads the `kernel` parameter from `config.txt` to find the kernel image file (for example, `kernel=Image.gz`). It also loads the device tree blob (`.dtb` file), a list of the board's hardware that the kernel reads to learn which drivers to start.

3. **Linux kernel boots (third stage)**

   The GPU releases the ARM cores from reset and passes control to the kernel entry point. The kernel (already unpacked by the firmware if the file is a compressed `Image.gz`, because a 64-bit ARM kernel cannot decompress itself) sets up the memory management unit (the hardware that gives each program its own memory), starts the CPU cores, and starts a driver for each device listed in the device tree. You will see kernel log messages on the serial console during this stage. The kernel mounts the root filesystem and looks for the `init` process.

4. **Init and userspace (fourth stage)**

   The kernel executes `/sbin/init` (or whatever the `init=` kernel command line parameter specifies). In a full Linux distribution this would be `systemd`, but in our minimal system it will be a BusyBox init that reads `/etc/inittab` and launches a shell. Your custom "hello from custom Linux" binary runs at this stage.
</Steps>

<Card title="Why the GPU boots first" icon="information">
The Broadcom chip was first designed for multimedia products, where the GPU had to start the display as fast as possible. For the hardware, the ARM processor is the second processor. This is why the Raspberry Pi boot looks different from most ARM boards, where a bootloader such as U-Boot runs on the ARM processor itself.
</Card>

## Setting Up the Cross-Toolchain

<InArticleAd />


A compiled program is a list of instructions for one family of processor. Your PC has an x86_64 processor and the Pi has an AArch64 (64-bit ARM) processor, and neither can run the other's instructions. The normal `gcc` on your PC produces x86 programs, which the Pi cannot run. A cross-compiler solves this: it runs on one machine (the **host**, your PC) and produces programs for another (the **target**, the Pi).

```text
  Cross-compilation: host and target
  ──────────────────────────────────────────
  Host PC (x86_64)          Target (AArch64)
  ─────────────────         ────────────────
  hello.c                   RPi Zero 2 W
    │                       Cortex-A53
    ▼
  aarch64-linux-gnu-gcc     Cannot run x86
    │                       programs
    ▼
  hello (AArch64 ELF) ─────► Runs here
    │
    ▼
  Cannot run on the host
```

A toolchain is the set of build tools: a compiler (`aarch64-linux-gnu-gcc`), a linker, an assembler, and supporting libraries. The prefix `aarch64-linux-gnu-` names the target: the AArch64 architecture, the Linux operating system, the GNU C library.

Install the toolchain on your host:

```bash
sudo apt update
sudo apt install -y gcc-aarch64-linux-gnu g++-aarch64-linux-gnu
```

Verify the installation:

```bash
aarch64-linux-gnu-gcc --version
```

You should see output similar to:

```
aarch64-linux-gnu-gcc (Ubuntu 12.3.0-1ubuntu1~22.04) 12.3.0
Copyright (C) 2022 Free Software Foundation, Inc.
```

Confirm it produces AArch64 binaries by checking the target:

```bash
aarch64-linux-gnu-gcc -dumpmachine
```

Expected output:

```
aarch64-linux-gnu
```

You will also need a few other packages for working with SD cards, serial consoles, and filesystem images:

```bash
sudo apt install -y minicom picocom dosfstools parted \
  debootstrap qemu-user-static binfmt-support
```

<Card title="Why not compile natively on the Pi?" icon="warning">
The Raspberry Pi Zero 2 W has only 512 MB of RAM and a slow CPU. A Linux kernel build that takes 5 minutes on your host could take over an hour on the Pi. And on a new board there is no system yet to compile on. Cross-compilation is the standard practice in embedded Linux.
</Card>

## Wiring the Serial Console

<InArticleAd />


A board that does not boot has no network, so it cannot tell you what went wrong. The serial console can: it is a UART on which the kernel prints its messages from the first moments of boot, and on which you later type commands. It needs three wires.

The Raspberry Pi Zero 2 W exposes a UART on its GPIO header:

| RPi GPIO Pin | Function | Connects To (USB-Serial Adapter) |
|-------------|----------|----------------------------------|
| GPIO14 (Pin 8) | TXD (Transmit) | RXD on adapter |
| GPIO15 (Pin 10) | RXD (Receive) | TXD on adapter |
| GND (Pin 6) | Ground | GND on adapter |

<Card title="Important wiring notes" icon="warning">
**TX connects to RX and RX connects to TX.** Wiring TX to TX is the most common mistake: the Pi's transmit pin must reach the adapter's receive pin.

The Raspberry Pi GPIO works at **3.3V logic levels**. A 5V serial adapter on the GPIO pins damages the chip. The CP2102 and most FTDI adapters have a 3.3V mode, so check your adapter before you connect it.

Do **not** connect the VCC/5V pin of the adapter to the Pi. The Pi takes its power from the micro-USB cable.
</Card>

After wiring, plug the USB-serial adapter into your host PC. It will appear as a device file, typically `/dev/ttyUSB0` or `/dev/ttyACM0`. Check which device appeared:

```bash
ls /dev/ttyUSB*
```

Open a serial terminal using `minicom`:

```bash
sudo minicom -b 115200 -D /dev/ttyUSB0
```

Or using `picocom` (simpler interface, recommended):

```bash
sudo picocom -b 115200 /dev/ttyUSB0
```

If you get a "permission denied" error, add your user to the `dialout` group:

```bash
sudo usermod -aG dialout $USER
```

Log out and log back in for the group change to take effect. After that you can run `picocom` without `sudo`.

The baud rate **115200** (bits per second) is the default of the Raspberry Pi firmware. The Pi and your terminal program must use the same rate, or you see wrong characters. The full setting is 8 data bits, no parity, 1 stop bit, written `115200 8N1`.

## Cross-Compiling Your First Binary

<InArticleAd />


The test program must prove that it runs on the ARM processor with a working kernel under it. So it asks the kernel for facts. `uname()` returns the kernel version and the machine type. The files `/proc/cpuinfo` and `/proc/meminfo` are not stored on the card: the kernel produces their text when a program reads them.

Create a working directory on your host:

```bash
mkdir -p ~/rpi-embedded/lesson1
cd ~/rpi-embedded/lesson1
```

Create the source file `hello_linux.c`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/utsname.h>

#define BUF_SIZE 256

void print_cpuinfo(void)
{
    FILE *fp;
    char line[BUF_SIZE];

    fp = fopen("/proc/cpuinfo", "r");
    if (fp == NULL) {
        perror("Cannot open /proc/cpuinfo");
        return;
    }

    printf("--- /proc/cpuinfo (selected fields) ---\n");
    while (fgets(line, sizeof(line), fp) != NULL) {
        if (strncmp(line, "processor", 9) == 0 ||
            strncmp(line, "model name", 10) == 0 ||
            strncmp(line, "Hardware", 8) == 0 ||
            strncmp(line, "CPU architecture", 16) == 0) {
            printf("  %s", line);
        }
    }
    fclose(fp);
}

void print_meminfo(void)
{
    FILE *fp;
    char line[BUF_SIZE];

    fp = fopen("/proc/meminfo", "r");
    if (fp == NULL) {
        perror("Cannot open /proc/meminfo");
        return;
    }

    printf("--- /proc/meminfo (first 3 lines) ---\n");
    for (int i = 0; i < 3 && fgets(line, sizeof(line), fp) != NULL; i++) {
        printf("  %s", line);
    }
    fclose(fp);
}

int main(void)
{
    struct utsname info;

    printf("========================================\n");
    printf("  Hello from custom Linux!\n");
    printf("========================================\n\n");

    if (uname(&info) == 0) {
        printf("System name:  %s\n", info.sysname);
        printf("Node name:    %s\n", info.nodename);
        printf("Release:      %s\n", info.release);
        printf("Version:      %s\n", info.version);
        printf("Machine:      %s\n\n", info.machine);
    } else {
        perror("uname failed");
    }

    print_cpuinfo();
    printf("\n");
    print_meminfo();

    return 0;
}
```

Cross-compile it:

```bash
aarch64-linux-gnu-gcc -o hello_linux hello_linux.c -static
```

A normal Linux program does not contain the C library. It loads the library from files on the root filesystem each time it starts. Your minimal root filesystem will not have those files, so the program would fail to start. The `-static` flag copies the library code into the program itself, so it needs no other file.

Verify the binary is an AArch64 ELF executable:

```bash
file hello_linux
```

Expected output:

```
hello_linux: ELF 64-bit LSB executable, ARM aarch64, version 1 (GNU/Linux),
statically linked, BuildID[sha1]=..., for GNU/Linux 3.7.0, not stripped
```

Look for three things: **64-bit**, **ARM aarch64**, and **statically linked**. If you see `x86-64`, you used the PC's own `gcc` and not the cross-compiler.

Check the size of the program:

```bash
ls -lh hello_linux
```

A statically linked program is larger (around 700 KB to 1 MB) because it includes the C library. Products often use a smaller C library such as musl. For this lesson the GNU C library (glibc) is fine.

## Building a Minimal Root Filesystem

<InArticleAd />


The shell, `ls`, the login prompt and your own program are ordinary files. They live in the root filesystem (rootfs), the directory tree that Linux mounts as `/` at boot. A kernel with no root filesystem prints its messages and then stops with a panic, because it has no first program to start.

A desktop system has tens of thousands of files there. An embedded system needs only:

- an `init` program,
- a shell and a few commands,
- the empty directories `/proc`, `/sys` and `/dev`, which the kernel fills with its own information at boot.

BusyBox is one program that does the work of hundreds of common Unix commands (sh, ls, cat, mount and many more), and it can also be the init.

<Steps>
1. **Create the rootfs directory structure**

   ```bash
   mkdir -p ~/rpi-embedded/rootfs
   cd ~/rpi-embedded/rootfs
   mkdir -p bin dev etc lib proc sys tmp sbin usr/bin usr/sbin var/log
   ```

2. **Download and install BusyBox (static binary)**

   Cross-compile BusyBox from its source. `ARCH` names the target processor family and `CROSS_COMPILE` is the prefix of your cross-compiler. `defconfig` selects the default set of commands:

   ```bash
   cd ~/rpi-embedded
   wget https://busybox.net/downloads/busybox-1.36.1.tar.bz2
   tar xjf busybox-1.36.1.tar.bz2
   cd busybox-1.36.1
   make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
   ```

   Enable static linking in the configuration:

   ```bash
   sed -i 's/# CONFIG_STATIC is not set/CONFIG_STATIC=y/' .config
   ```

   Build BusyBox:

   ```bash
   make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
   ```

   Install it into your rootfs:

   ```bash
   make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     CONFIG_PREFIX=~/rpi-embedded/rootfs install
   ```

   This creates `bin/busybox` and hundreds of symlinks (names such as `bin/sh`, `bin/ls`, `sbin/init` that all point to the BusyBox program). BusyBox looks at the name it was called by and behaves as that command.

3. **Copy your hello binary**

   ```bash
   cp ~/rpi-embedded/lesson1/hello_linux ~/rpi-embedded/rootfs/bin/
   chmod +x ~/rpi-embedded/rootfs/bin/hello_linux
   ```

4. **Create `/etc/inittab`**

   This file tells BusyBox init what to do at startup:

   ```bash
   cat > ~/rpi-embedded/rootfs/etc/inittab << 'INITTAB'
   ::sysinit:/etc/init.d/rcS
   ::respawn:/sbin/getty -L console 115200 vt100
   ::shutdown:/bin/umount -a -r
   INITTAB
   ```

   The three lines mean: run the startup script once, then start a login prompt on the console (and start it again each time it exits), and unmount all filesystems on shutdown.

5. **Create the startup script**

   ```bash
   mkdir -p ~/rpi-embedded/rootfs/etc/init.d
   cat > ~/rpi-embedded/rootfs/etc/init.d/rcS << 'RCS'
   #!/bin/sh

   echo "Mounting virtual filesystems..."
   mount -t proc none /proc
   mount -t sysfs none /sys
   mount -t devtmpfs none /dev

   echo ""
   /bin/hello_linux
   echo ""
   echo "System ready."
   RCS
   chmod +x ~/rpi-embedded/rootfs/etc/init.d/rcS
   ```

   The script first mounts the three virtual filesystems, the directories that the kernel fills with its own information. `/proc/cpuinfo` exists only after `/proc` is mounted, so the order matters. Then it runs your hello program.

6. **Create a basic passwd file**

   ```bash
   cat > ~/rpi-embedded/rootfs/etc/passwd << 'PASSWD'
   root::0:0:root:/root:/bin/sh
   PASSWD

   cat > ~/rpi-embedded/rootfs/etc/group << 'GROUP'
   root:x:0:
   GROUP

   mkdir -p ~/rpi-embedded/rootfs/root
   ```

   This creates a root user with no password. That is acceptable on a bench and never in a product.
</Steps>

Your rootfs directory should now look like this:

<FileTree>
- rootfs/
  - bin/
    - busybox
    - hello_linux
    - sh
    - ls
    - mount
  - dev/
  - etc/
    - inittab
    - passwd
    - group
    - init.d/
      - rcS
  - lib/
  - proc/
  - root/
  - sbin/
    - init
    - getty
  - sys/
  - tmp/
  - usr/
    - bin/
    - sbin/
  - var/
    - log/
</FileTree>

Note that `bin/sh`, `sbin/init`, `sbin/getty`, and many other files are symlinks to `bin/busybox`.

## Preparing the SD Card

<InArticleAd />


The microSD card needs two partitions, because two different readers use it. The GPU firmware can read only the simple FAT32 format, so the files it loads (the firmware itself, the device tree, the kernel and `config.txt`) go on a small FAT32 boot partition. Linux needs file owners, permissions and symlinks, which FAT32 cannot store, so your rootfs goes on a larger partition in the Linux format ext4.

<Card title="Warning: this will erase the SD card" icon="danger">
The following commands will destroy all data on the SD card. Double-check the device name before running them. If your SD card is `/dev/sdb`, make absolutely sure it is not your system drive. You can verify by checking the size with `lsblk`.
</Card>

Insert the SD card and identify its device name:

```bash
lsblk
```

Look for the newly appeared device (typically `/dev/sdb` or `/dev/mmcblk0`). In the commands below, replace `/dev/sdX` with your actual device.

<Steps>
1. **Partition the SD card**

   ```bash
   sudo parted /dev/sdX --script mklabel msdos
   sudo parted /dev/sdX --script mkpart primary fat32 1MiB 128MiB
   sudo parted /dev/sdX --script mkpart primary ext4 128MiB 100%
   ```

   This creates a FAT32 boot partition from 1 MiB to 128 MiB (127 MiB) and uses the remaining space for the ext4 root partition.

2. **Format the partitions**

   ```bash
   sudo mkfs.vfat -F 32 -n BOOT /dev/sdX1
   sudo mkfs.ext4 -L rootfs /dev/sdX2
   ```

3. **Mount the partitions**

   ```bash
   sudo mkdir -p /mnt/boot /mnt/rootfs
   sudo mount /dev/sdX1 /mnt/boot
   sudo mount /dev/sdX2 /mnt/rootfs
   ```

4. **Download Raspberry Pi firmware files**

   The boot partition needs the GPU firmware files. Raspberry Pi publishes them only in compiled form. Clone the firmware repository:

   ```bash
   cd ~/rpi-embedded
   git clone --depth 1 https://github.com/raspberrypi/firmware.git rpi-firmware
   ```

   Copy the required firmware files to the boot partition:

   ```bash
   sudo cp rpi-firmware/boot/bootcode.bin /mnt/boot/
   sudo cp rpi-firmware/boot/start.elf /mnt/boot/
   sudo cp rpi-firmware/boot/fixup.dat /mnt/boot/
   sudo cp rpi-firmware/boot/start_cd.elf /mnt/boot/
   sudo cp rpi-firmware/boot/fixup_cd.dat /mnt/boot/
   ```

   The `_cd` (cut-down) pair is required because `gpu_mem=16` in the `config.txt` below makes the firmware load `start_cd.elf` and `fixup_cd.dat` instead of the standard files. Without them the board does not boot.

5. **Copy the kernel and device tree**

   For now, use the ready-built kernel from the firmware repository. You compile your own in [kernel configuration and custom build](/education/embedded-linux-rpi/kernel-configuration-custom-build/).

   ```bash
   sudo cp rpi-firmware/boot/kernel8.img /mnt/boot/
   sudo cp rpi-firmware/boot/bcm2710-rpi-zero-2-w.dtb /mnt/boot/
   sudo mkdir -p /mnt/boot/overlays
   sudo cp rpi-firmware/boot/overlays/* /mnt/boot/overlays/
   ```

   The file `kernel8.img` is the 64-bit kernel. The `.dtb` file is the device tree blob specific to the Zero 2 W.

6. **Create `config.txt`**

   ```bash
   sudo tee /mnt/boot/config.txt > /dev/null << 'CONFIG'
   # Raspberry Pi Zero 2 W boot configuration
   arm_64bit=1
   kernel=kernel8.img
   enable_uart=1
   dtoverlay=miniuart-bt
   gpu_mem=16
   disable_splash=1
   boot_delay=0
   CONFIG
   ```

7. **Create `cmdline.txt`**

   This file contains the kernel command line parameters:

   ```bash
   echo "console=serial0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait init=/sbin/init" | sudo tee /mnt/boot/cmdline.txt
   ```

   Everything must be on a **single line**. The parameters tell the kernel to print its messages on the serial port, to mount the second SD card partition as the root filesystem, to wait until the card is ready (`rootwait`), and to start `/sbin/init` as the first program.

8. **Copy rootfs to the root partition**

   ```bash
   sudo cp -a ~/rpi-embedded/rootfs/* /mnt/rootfs/
   ```

   The `-a` flag preserves permissions, ownership, and symlinks.

9. **Unmount and sync**

   ```bash
   sudo umount /mnt/boot
   sudo umount /mnt/rootfs
   sync
   ```
</Steps>

## First Boot

<InArticleAd />


<Steps>
1. Insert the microSD card into the Raspberry Pi Zero 2 W.
2. Connect the USB-serial adapter wires (TX, RX, GND) as described in the wiring section.
3. Open your serial terminal on the host: `picocom -b 115200 /dev/ttyUSB0`
4. Plug in the micro-USB power cable to the Pi.
</Steps>

Boot messages appear in your terminal. Read the output below in three parts. The lines that start with a number in brackets come from the kernel, and the number is the time in seconds since the kernel started. The `EXT4-fs` and `VFS` lines show the root filesystem being mounted. Everything after "Mounting virtual filesystems..." comes from your own startup script and program.

```
[    0.000000] Booting Linux on physical CPU 0x0000000000 [0x410fd034]
[    0.000000] Linux version 6.6.x-v8+ (gcc version 12.3.0) #1 SMP PREEMPT ...
[    0.000000] Machine model: Raspberry Pi Zero 2 W Rev 1.0
[    0.000000] Memory: 440560K/507904K available ...
```

<Card title="Troubleshooting" icon="warning">
**No output at all:** Check your TX/RX wiring (swap them if needed). Verify the adapter is 3.3V. Confirm the baud rate is 115200.

**Garbled characters:** Baud rate mismatch. Make sure both sides use 115200.

**Kernel panic, no init found:** The root filesystem path in `cmdline.txt` is wrong, or `/sbin/init` does not exist in the rootfs. Verify your `cmdline.txt` says `root=/dev/mmcblk0p2` and that you copied the rootfs correctly.

**Kernel boots but no "Hello" message:** The init script `/etc/init.d/rcS` might not be executable. Re-mount the SD card on your host and run `chmod +x` on it.

## How config.txt Works

<InArticleAd />


The `config.txt` file is not a Linux configuration file. The GPU firmware (`start.elf`) reads it before the ARM processor starts, so Linux never sees it. It does the work that the BIOS settings do on a PC. These are the lines you wrote:

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `arm_64bit=1` | 1 | Boot in 64-bit (AArch64) mode. Without this, the Pi boots in 32-bit mode even though the Cortex-A53 supports 64-bit. |
| `kernel=kernel8.img` | filename | Specifies which kernel image file to load from the boot partition. |
| `enable_uart=1` | 1 | Enables the primary UART (serial port) on GPIO14/15. This is essential for serial console access. |
| `dtoverlay=miniuart-bt` | overlay name | Moves Bluetooth to the mini UART and gives the full PL011 UART to the serial console. The PL011 is more reliable because it has a proper clock source. |
| `gpu_mem=16` | MB | Allocates only 16 MB of RAM to the GPU, leaving the rest for the ARM cores. Since we are running a headless embedded system, the GPU needs minimal memory. |
| `disable_splash=1` | 1 | Skips the rainbow splash screen, saving a fraction of a second during boot. |
| `boot_delay=0` | seconds | Eliminates the default 1-second delay before loading the kernel. |

The full list of parameters is in the [Raspberry Pi config.txt documentation](https://www.raspberrypi.com/documentation/computers/config_txt.html). Three more are useful for embedded work:

```ini
# Set fixed core frequency (avoids clock scaling during timing-sensitive work)
force_turbo=1
arm_freq=1000

# Disable HDMI to save power (about 25 mA)
hdmi_blanking=2

# Disable camera and display interfaces
start_x=0
```

<Card title="config.txt vs cmdline.txt" icon="information">
The two files have different readers. The GPU firmware reads `config.txt` to set up hardware before Linux starts. The firmware passes the text of `cmdline.txt` to the Linux kernel as its command line. Hardware settings go in `config.txt`. Settings for the kernel go in `cmdline.txt`.
</Card>
