You wire a sensor to a Linux board, the kernel already contains its driver, and nothing happens. No error, no reading. The driver never started, because nothing told the kernel that the sensor exists. A sensor on an I2C bus cannot announce itself as a USB device does, so the kernel needs a written list of the hardware: what exists, at which address, and which driver manages it. That list is the device tree. In this lesson you read the base device tree of the Raspberry Pi Zero 2 W and write a small addition, an overlay, that declares a BME280 sensor on I2C bus 1. After the next boot the kernel starts the driver by itself, and you read temperature, pressure and humidity from plain files. #DeviceTree #I2C #EmbeddedLinux

## What is a Device Tree?

<InArticleAd />


On a microcontroller such as the ATmega328P, your firmware is compiled for one chip. The datasheet says that PORTB is at address 0x25 and TWBR at 0xB8, and you write those addresses into the code.

A Linux kernel cannot work that way, because the same kernel image must run on hundreds of boards: a Raspberry Pi, a BeagleBone, a custom industrial board. Each has different peripherals at different addresses. So the kernel carries no board addresses in its code. At boot it receives a description that says: "This board has 4 CPUs. It has an I2C controller at address 0x7e804000. GPIO pins 2 and 3 belong to that I2C controller."

That description is the **device tree**. It is data, not code: it lists hardware and starts no driver by itself. The kernel reads it and starts a driver for each entry it recognizes.

<CardGrid>
  <Card title="Without Device Trees" icon="warning">
    Every board needs a custom-compiled kernel with hardware details baked into C source files. Adding a new board means modifying kernel code, recompiling, and maintaining a fork.
  </Card>
  <Card title="With Device Trees" icon="approve">
    One kernel binary works across many boards. Hardware details live in a separate `.dtb` file that the bootloader passes to the kernel. Adding a new board means writing a new `.dts` text file and compiling it.
  </Card>
</CardGrid>

The board maker writes the base tree. It describes everything on the board itself, and it leaves the I2C bus switched off because nothing is connected to it yet:

```text
  Base tree: bcm2710-rpi-zero-2-w.dts
  ─────────────────────────────────────
  ┌───────────────────────────────┐
  │ / {                           │
  │   cpus { cpu@0 { ... }; };    │
  │   soc {                       │
  │     i2c1: i2c@7e804000 {      │
  │       status = "disabled";    │
  │     };                        │
  │   };                          │
  │ };                            │
  └───────────────────────────────┘
```

What you connect to the header is not on that list. You describe it in an overlay, a small file that is added to the base tree at boot. This one switches the bus on and adds the sensor under it:

```text
  Overlay: my-overlay.dts
  ─────────────────────────────────────
  ┌───────────────────────────────┐
  │ &i2c1 {                       │
  │   status = "okay";            │
  │   bme280@76 {                 │
  │     compatible = "bosch,..."; │
  │     reg = <0x76>;             │
  │   };                          │
  │ };                            │
  └───────────────────────────────┘
  base + overlay = the tree the kernel sees
```

<Card title="Key Terminology" icon="information">

| Term | Meaning |
|------|---------|
| DTS | Device Tree Source, the human-readable text file (.dts) |
| DTB | Device Tree Blob, the compiled binary (.dtb) |
| DTBO | Device Tree Blob Overlay, a compiled overlay fragment (.dtbo) |
| DTC | Device Tree Compiler, the tool that converts DTS to DTB |
| Node | A block in the tree representing a device or bus |
| Property | A key-value pair inside a node |

</Card>

You write the text form and the kernel reads the binary form:

```text
  DTS Compilation and Loading
  ──────────────────────────────────────────
  my-overlay.dts  (text, you edit this)
       │
       ▼
  dtc -I dts -O dtb -o my-overlay.dtbo
       │
       ▼
  my-overlay.dtbo (binary, kernel reads this)
       │
       │  config.txt: dtoverlay=my-overlay
       ▼
  Bootloader merges overlay with base DTB
       │
       ▼
  Kernel sees merged tree at /proc/device-tree
```

## DTS Syntax Primer

<InArticleAd />


A device tree source file is a text file with a tree structure. The example describes a small board with memory, a GPIO controller and one LED. Notice that the LED points to the GPIO controller by name (`&gpio`) and gives a pin number.

### Minimal Example

```dts
/dts-v1/;

/ {
    model = "Minimal Example Board";
    compatible = "example,minimal";
    #address-cells = <1>;
    #size-cells = <1>;

    memory@0 {
        device_type = "memory";
        reg = <0x0 0x20000000>;
    };

    gpio: gpio@7e200000 {
        compatible = "brcm,bcm2835-gpio";
        reg = <0x7e200000 0xb4>;
        gpio-controller;
        #gpio-cells = <2>;
    };

    leds {
        compatible = "gpio-leds";

        status_led: led0 {
            label = "status";
            gpios = <&gpio 27 0>;
            default-state = "off";
        };
    };
};
```

The syntax rules, one at a time:

### Version Tag

```dts
/dts-v1/;
```

This must be the first line. It tells the compiler that the file uses the current DTS syntax.

### Root Node

```dts
/ {
    ...
};
```

The forward slash is the root of the tree. A device tree has exactly one root node, and all other nodes are inside it.

### Child Nodes

Nodes are defined with a name and optional unit address:

```dts
memory@0 {
    ...
};
```

The `@0` is the **unit address**. It is part of the node's name and should equal the first value in the `reg` property. It keeps two nodes with the same base name apart (`serial@7e201000` and `serial@7e215040`).

### Properties

Properties are key-value pairs inside a node. The value can be several types:

```dts
/* String */
compatible = "bosch,bme280";

/* String list */
compatible = "vendor,specific", "vendor,generic";

/* 32-bit integer cells (in angle brackets) */
reg = <0x7e804000 0x1000>;

/* Byte string */
local-mac-address = [00 11 22 33 44 55];

/* Empty (boolean: property exists = true) */
gpio-controller;
```

### The `compatible` Property

This is the most important property, because it is how a node gets its driver. The format is `"manufacturer,device"`:

```dts
compatible = "bosch,bme280";
```

Every driver carries a list of the compatible strings it can handle (its `of_match_table`). When the kernel meets this node, it looks for a driver whose list contains `"bosch,bme280"` and gives the device to that driver. If the string differs by one character, no driver starts and no error is printed.

### The `reg` Property

Says where the device is: its address and, where it has one, the length of its address range.

```dts
reg = <address length>;
```

For a peripheral inside the chip, it is the first address and the number of bytes it occupies:

```dts
reg = <0x7e804000 0x1000>;
```

For an I2C device, `reg` is only the I2C address of the device on the bus:

```dts
reg = <0x76>;
```

The parent node decides how many numbers `reg` has: `#address-cells` for the address and `#size-cells` for the length. An I2C bus sets them to 1 and 0.

### The `status` Property

Controls whether the kernel activates a device:

| Value | Meaning |
|-------|---------|
| `"okay"` | Device is present and should be enabled |
| `"disabled"` | Device exists but should not be activated |

Many nodes in the base device tree are set to `"disabled"` by default. An overlay sets them to `"okay"` when the hardware is actually connected.

### Labels and Phandles

A device often needs something from another device: an LED needs a pin of the GPIO controller. So a node can get a label, a short name placed before it:

```dts
gpio: gpio@7e200000 {
    ...
    #gpio-cells = <2>;
};
```

Other nodes reference this label with `&gpio`:

```dts
gpios = <&gpio 27 0>;
```

Read this as: pin 27 of the controller labelled `gpio`, with flags 0 (`#gpio-cells = <2>` says that two numbers follow the reference). The compiler replaces the label reference with a number, the **phandle**. You never write phandle numbers yourself.

## Reading the Base Device Tree

<InArticleAd />


The Raspberry Pi Zero 2 W uses the BCM2710A1 SoC. The base device tree source lives in the Linux kernel source tree:

```
arch/arm/boot/dts/broadcom/bcm2710-rpi-zero-2-w.dts
```

Much of the description is the same for every board with this chip family, so the board file is short and includes shared files (`.dtsi`):

<FileTree>
- arch/arm/boot/dts/broadcom/
  - bcm2710-rpi-zero-2-w.dts
  - bcm2710.dtsi
  - bcm2709.dtsi
  - bcm2835-common.dtsi
  - bcm2835-rpi.dtsi
</FileTree>

You can browse the kernel source online or clone the Raspberry Pi kernel repository:

```bash
git clone --depth 1 https://github.com/raspberrypi/linux.git rpi-linux
```

### Key Nodes in the Base Tree

Four nodes are worth reading. In each, find `compatible` (which driver), `reg` (where) and `status` (on or off).

**CPU cluster:**

```dts
cpus {
    #address-cells = <1>;
    #size-cells = <0>;

    cpu@0 {
        device_type = "cpu";
        compatible = "arm,cortex-a53";
        reg = <0x0>;
        enable-method = "spin-table";
    };
    /* cpu@1, cpu@2, cpu@3 follow the same pattern */
};
```

**GPIO controller:**

```dts
gpio: gpio@7e200000 {
    compatible = "brcm,bcm2835-gpio";
    reg = <0x7e200000 0xb4>;
    gpio-controller;
    #gpio-cells = <2>;
    interrupt-controller;
    #interrupt-cells = <2>;
};
```

**I2C1 bus (the one exposed on the GPIO header):**

```dts
i2c1: i2c@7e804000 {
    compatible = "brcm,bcm2835-i2c";
    reg = <0x7e804000 0x1000>;
    clocks = <&clocks BCM2835_CLOCK_VPU>;
    #address-cells = <1>;
    #size-cells = <0>;
    status = "disabled";
};
```

Notice that `status = "disabled"`. The base tree ships I2C1 as disabled. The Raspberry Pi firmware's `config.txt` option `dtparam=i2c_arm=on` sets a parameter of the base device tree that changes this to `"okay"`.

**SPI0 bus:**

```dts
spi0: spi@7e204000 {
    compatible = "brcm,bcm2835-spi";
    reg = <0x7e204000 0x200>;
    clocks = <&clocks BCM2835_CLOCK_VPU>;
    #address-cells = <1>;
    #size-cells = <0>;
    status = "disabled";
};
```

### How the Bootloader Merges Overlays

The merge is done by the GPU firmware, before Linux starts:

<Steps>
1. The GPU firmware reads `config.txt` from the boot partition.
2. It loads the base DTB file (e.g., `bcm2710-rpi-zero-2-w.dtb`) into memory.
3. For each `dtoverlay=` line in `config.txt`, it loads the corresponding `.dtbo` file from `/boot/overlays/`.
4. It merges each overlay into the base tree in order, modifying or adding nodes.
5. It gives the kernel the address of the final merged tree (in processor register x0 on a 64-bit system).
6. The kernel reads the tree and starts a driver for every node with `status = "okay"`.
</Steps>

So you never change the base DTB. You write small overlay files that change or add specific parts of the tree.

## Device Tree Compiler (dtc)

<InArticleAd />


The device tree compiler (`dtc`) converts between DTS (text) and DTB (binary) formats. Install it on your development machine or directly on the Pi:

<Tabs>
<TabItem label="Raspberry Pi (on-device)">
```bash
sudo apt update
sudo apt install device-tree-compiler
```
</TabItem>
<TabItem label="Ubuntu/Debian (host)">
```bash
sudo apt update
sudo apt install device-tree-compiler
```
</TabItem>
</Tabs>

### Compile DTS to DTB

For a full device tree:

```bash
dtc -I dts -O dtb -o output.dtb input.dts
```

For an overlay (use the `-@` flag to preserve symbols for phandle resolution):

```bash
dtc -@ -I dts -O dtb -o overlay.dtbo overlay.dts
```

A compiled tree normally loses its labels. The `-@` flag keeps them, in a `__symbols__` node. The base DTB is built with this flag, which is how the firmware can find `&i2c1` at boot. Use it for your overlays too, so that their own labels (such as `bme280`) stay visible to overlay parameters and to later overlays.

### Decompile DTB to DTS

The compiler also works backwards. Use this to read what a binary file on the card really contains:

```bash
dtc -I dtb -O dts -o readable.dts /boot/bcm2710-rpi-zero-2-w.dtb
```

You can also decompile an overlay:

```bash
dtc -I dtb -O dts -o readable.dts /boot/overlays/i2c-sensor.dtbo
```

### Verify a DTS File

Check for syntax errors without producing output:

```bash
dtc -@ -I dts -O dtb -o /dev/null my-overlay.dts
```

Any warnings or errors will be printed to stderr.

## Writing a BME280 I2C Overlay

<InArticleAd />


Now write the overlay that tells the kernel: "There is a Bosch BME280 sensor at I2C address 0x76 on the I2C1 bus."

An overlay has more wrapping than the base tree, because it must say where in the base tree its content goes. Create a file called `bme280-sensor.dts`:

```dts title="bme280-sensor.dts"
/dts-v1/;
/plugin/;

/ {
    compatible = "brcm,bcm2835";

    fragment@0 {
        target = <&i2c1>;

        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;
            status = "okay";

            bme280: bme280@76 {
                compatible = "bosch,bme280";
                reg = <0x76>;
                status = "okay";
            };
        };
    };
};
```

Line by line:

**`/dts-v1/;`**: Required version tag.

**`/plugin/;`**: Marks this file as an overlay (not a standalone device tree). This tells the compiler that unresolved references like `&i2c1` are expected and will be resolved against the base tree at boot time.

**`compatible = "brcm,bcm2835";`**: Declares which base device tree this overlay is compatible with. The BCM2710 (Pi Zero 2 W) is backward-compatible with BCM2835.

**`fragment@0`**: An overlay can contain multiple fragments. Each fragment targets a specific node in the base tree.

**`target = <&i2c1>;`**: This fragment's changes will be applied to the `i2c1` node in the base tree. The `&i2c1` reference resolves to the phandle of the I2C1 controller node.

**`__overlay__ { ... }`**: Everything inside this block gets merged into the target node. Properties listed here override existing properties in the target. New child nodes are added.

**`#address-cells = <1>;` and `#size-cells = <0>;`**: These tell the device tree parser that child nodes of this bus have 1-cell addresses (the I2C slave address) and no size component.

**`status = "okay";`**: Enables the I2C1 bus itself (overriding the base tree's `"disabled"`).

**`bme280@76`**: A child node representing the sensor. The `@76` is the unit address matching `reg`.

**`compatible = "bosch,bme280";`**: The kernel's BME280 IIO driver registers itself for this compatible string. When the kernel sees this node, it loads the `bmp280-i2c` driver module (one driver covers the BMP280 and BME280 families).

**`reg = <0x76>;`**: The I2C slave address. If you have connected the SDO pin of your BME280 module to VCC, use `<0x77>` instead.

### Compile the Overlay

```bash
dtc -@ -I dts -O dtb -o bme280-sensor.dtbo bme280-sensor.dts
```

If the compilation succeeds with no errors, you will have a `bme280-sensor.dtbo` file ready for deployment.

## Loading the Overlay

<InArticleAd />


<Steps>
1. Copy the compiled overlay to the boot partition:

   ```bash
   sudo cp bme280-sensor.dtbo /boot/overlays/
   ```

2. Edit `/boot/config.txt` (or `/boot/firmware/config.txt` on newer OS images) to load the overlay:

   ```bash
   sudo nano /boot/config.txt
   ```

   Add these lines (if `dtparam=i2c_arm=on` is not already present, add it too):

   ```ini title="/boot/config.txt"
   dtparam=i2c_arm=on
   dtoverlay=bme280-sensor
   ```

3. Reboot the Pi:

   ```bash
   sudo reboot
   ```

4. After reboot, verify the sensor was detected on the I2C bus:

   ```bash
   sudo apt install -y i2c-tools
   i2cdetect -y 1
   ```

   You should see `76` (or `UU` if a driver has claimed it) in the output grid at row 70, column 6.

5. Check that the IIO driver loaded:

   ```bash
   ls /sys/bus/iio/devices/
   ```

   You should see a directory like `iio:device0`.

6. Read sensor values:

   ```bash
   # Temperature in millidegrees Celsius
   cat /sys/bus/iio/devices/iio:device0/in_temp_input

   # Pressure in kiloPascals
   cat /sys/bus/iio/devices/iio:device0/in_pressure_input

   # Relative humidity in percent (times 1000)
   cat /sys/bus/iio/devices/iio:device0/in_humidityrelative_input
   ```

   A temperature reading of `23450` means 23.45 degrees Celsius.
</Steps>

If the IIO device does not appear, check `dmesg` for errors:

```bash
dmesg | grep -i bmp280
dmesg | grep -i i2c
```

The usual causes are:

- the BME280 module is wired wrongly,
- the I2C bus is not enabled,
- the kernel was built without the `bmp280` driver, or has it as a module that is not loaded (load it with `sudo modprobe bmp280-i2c`).

## Pin Multiplexing (pinctrl)

<InArticleAd />


A chip has more internal peripherals than pins, so most pins can do one of several jobs. GPIO2 and GPIO3 on the BCM2710 can be general-purpose I/O pins, or the SDA1 and SCL1 lines of the I2C1 controller. If they are left as plain I/O, the signals of the I2C controller reach no pin. Choosing the job of a pin is called **pin multiplexing**, and the part of the kernel that does it is called **pinctrl**.

### How I2C1 Pins Are Configured in the Base DTS

In the BCM2835 base device tree, the pin configuration for I2C1 is defined in the GPIO node:

```dts
gpio: gpio@7e200000 {
    compatible = "brcm,bcm2835-gpio";
    /* ... */

    i2c1_pins: i2c1 {
        brcm,pins = <2 3>;
        brcm,function = <4>;  /* ALT0 = I2C1 SDA/SCL */
    };
};
```

The `brcm,pins` property lists GPIO2 and GPIO3. The `brcm,function` value `4` corresponds to ALT0, which maps these pins to the I2C1 peripheral.

The I2C1 node then references this pin configuration:

```dts
i2c1: i2c@7e804000 {
    compatible = "brcm,bcm2835-i2c";
    reg = <0x7e804000 0x1000>;
    pinctrl-names = "default";
    pinctrl-0 = <&i2c1_pins>;
    /* ... */
};
```

The `pinctrl-0 = <&i2c1_pins>` line tells the kernel: "When this device is active, configure the pins as specified in the `i2c1_pins` node."

### Adding pinctrl to a Custom Overlay

If your peripheral needs pins that the base tree does not assign, add a pinctrl node to your overlay. The example has two fragments, because it changes two places in the base tree: the first adds a pin group for SPI0 to the GPIO node, and the second tells the SPI0 node to use that group.

```dts
/dts-v1/;
/plugin/;

/ {
    compatible = "brcm,bcm2835";

    fragment@0 {
        target = <&gpio>;

        __overlay__ {
            my_spi_pins: my_spi_pins {
                brcm,pins = <9 10 11>;
                brcm,function = <4>;  /* ALT0 = SPI0 */
            };
        };
    };

    fragment@1 {
        target = <&spi0>;

        __overlay__ {
            pinctrl-names = "default";
            pinctrl-0 = <&my_spi_pins>;
            status = "okay";
        };
    };
};
```

The BME280 overlay needs no pinctrl of its own. The base device tree already assigns GPIO2 and GPIO3 to I2C1 through `pinctrl-0 = <&i2c1_pins>`, so the bus only has to be enabled. You need your own pinctrl node when you use other pins or design your own carrier board.

## Overlay Parameters

<InArticleAd />


Some BME280 modules answer at 0x76 and others at 0x77. Without parameters you would need two overlay files that differ in one number. On the Raspberry Pi an overlay can declare parameters in an `__overrides__` node, and the user sets them in `config.txt`.

### Making the I2C Address Configurable

This is the same overlay with one added node at the end:

```dts title="bme280-sensor-param.dts"
/dts-v1/;
/plugin/;

/ {
    compatible = "brcm,bcm2835";

    fragment@0 {
        target = <&i2c1>;

        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;
            status = "okay";

            bme280: bme280@76 {
                compatible = "bosch,bme280";
                reg = <0x76>;
                status = "okay";
            };
        };
    };

    __overrides__ {
        addr = <&bme280>,"reg:0";
    };
};
```

The `__overrides__` node maps parameter names to property targets:

- `addr` is the parameter name used in `config.txt`.
- `<&bme280>` is a phandle pointing to the `bme280` node.
- `"reg:0"` means "the first cell (byte offset 0) of the `reg` property."

### Using the Parameter

In `config.txt`, you can now specify the address:

```ini title="/boot/config.txt"
# Use default address 0x76
dtoverlay=bme280-sensor-param

# Or override to 0x77 (SDO tied to VCC)
dtoverlay=bme280-sensor-param,addr=0x77
```

Compile this version the same way:

```bash
dtc -@ -I dts -O dtb -o bme280-sensor-param.dtbo bme280-sensor-param.dts
sudo cp bme280-sensor-param.dtbo /boot/overlays/
```

### Multiple Parameters

You can add more parameters. For example, to allow enabling or disabling the sensor:

```dts
__overrides__ {
    addr   = <&bme280>,"reg:0";
    enable = <&bme280>,"status";
};
```

Usage:

```ini
dtoverlay=bme280-sensor-param,addr=0x77,enable=okay
```

## Debugging Device Trees

<InArticleAd />


A wrong device tree gives no error message: the driver does not start. So check in this order: is the node in the tree the kernel received, is its content right, and did a driver take it?

### Inspecting /proc/device-tree

The running kernel shows the tree it received as directories and files under `/proc/device-tree/`. Each node is a directory and each property is a file:

```bash
# List top-level nodes
ls /proc/device-tree/

# Check model
cat /proc/device-tree/model

# Check if i2c1 is enabled
cat /proc/device-tree/soc/i2c@7e804000/status

# Check if your bme280 node exists
ls /proc/device-tree/soc/i2c@7e804000/bme280@76/

# Read its compatible string
cat /proc/device-tree/soc/i2c@7e804000/bme280@76/compatible
```

### Dumping the Runtime Tree

You can decompile the entire runtime device tree back to readable DTS format:

```bash
dtc -I fs /proc/device-tree -O dts -o runtime-tree.dts
```

The file is the tree after all overlays were merged. Search it for your sensor node:

```bash
grep -A 5 "bme280" runtime-tree.dts
```

### Common Errors and Solutions

<CardGrid>
  <Card title="Wrong compatible string" icon="error">
    **Symptom:** Node appears in `/proc/device-tree/` but no driver binds. `dmesg` shows no related messages.
    **Fix:** Check that the `compatible` string exactly matches what the driver expects. For BME280, it must be `"bosch,bme280"` (check the match table in `drivers/iio/pressure/bmp280-i2c.c` in the kernel source).
  </Card>
  <Card title="Missing status property" icon="error">
    **Symptom:** Node exists in the tree but driver does not load.
    **Fix:** Ensure `status = "okay"` is set on both the bus node (i2c1) and the device node (bme280).
  </Card>
  <Card title="Overlay not loading" icon="error">
    **Symptom:** No trace of your node in `/proc/device-tree/`.
    **Fix:** Check that the `.dtbo` filename matches the `dtoverlay=` line in `config.txt` (without the extension). Verify the file is in `/boot/overlays/`. Check `/boot/config.txt` for typos.
  </Card>
  <Card title="Address conflict" icon="error">
    **Symptom:** `i2cdetect` shows nothing at the expected address.
    **Fix:** Verify physical wiring. Check that the BME280 module's SDO pin matches your configured address (GND = 0x76, VCC = 0x77). Ensure pull-up resistors are present on SDA/SCL (most breakout boards include them).
  </Card>
</CardGrid>

### Useful dmesg Filters

```bash
# All device tree related messages
dmesg | grep -i "of:"

# I2C subsystem messages
dmesg | grep -i i2c

# IIO subsystem (where bme280 registers)
dmesg | grep -i iio

# Failed driver probes
dmesg | grep -i "probe"
```
