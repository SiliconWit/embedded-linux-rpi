A machine that needs six seconds after power-on before it reacts feels broken to the person who switched it on. Much of that time is the kernel starting drivers for sound, cameras, Bluetooth and thousands of other devices that your board will never have. The ready-built Raspberry Pi kernel must serve every user, so it includes them all, and each one costs boot time and memory. In this lesson you get the kernel source, learn how its configuration system (Kconfig) organizes over 15,000 options, and use the menuconfig tool to keep only what your board needs. The result is your own kernel image that reaches the shell prompt in under 4 seconds. #LinuxKernel #Menuconfig #EmbeddedLinux

## What We Are Building

<Card title="Stripped-Down Kernel with Sub-4-Second Boot" icon="star">
A custom-compiled Linux kernel for the Raspberry Pi Zero 2 W, configured with only the subsystems and drivers needed for serial console, GPIO, I2C, SPI, and SD card storage. By disabling network file systems, sound, USB gadget classes, and dozens of other unused subsystems, the kernel image shrinks significantly and the time from power-on to shell prompt drops below 4 seconds.
</Card>

## Cloning the Kernel Source

<InArticleAd />


The kernel is the one program that touches the hardware. It shares the processor and the memory among all other programs, and it contains the drivers, the pieces of code that each know how to operate one device. A driver that is compiled in is started at boot, whether its device is connected or not. That is the cost you will remove.

The kernel is built from source code, so you can choose what goes in. Raspberry Pi maintains its own copy of the Linux source, with drivers for the Broadcom chips that the main Linux source does not yet include. Use this copy for any Pi project.

Clone the repository with the `rpi-6.6.y` branch (kernel version 6.6):

```bash
cd ~/rpi-embedded
git clone --depth 1 --branch rpi-6.6.y \
  https://github.com/raspberrypi/linux.git rpi-linux
cd rpi-linux
```

The `--depth 1` flag creates a shallow clone, downloading only the latest commit rather than the full history. This reduces the download from several gigabytes to roughly 200 MB.

Check which branch you are on:

```bash
git branch
```

Expected output:

```
* rpi-6.6.y
```

These are the directories that matter for embedded work:

<FileTree>
- rpi-linux/
  - arch/
    - arm64/
      - boot/
        - dts/
          - broadcom/
      - configs/
  - drivers/
    - gpio/
    - i2c/
    - spi/
    - mmc/
    - tty/
      - serial/
  - fs/
  - include/
  - init/
  - kernel/
  - mm/
  - net/
  - scripts/
  - Kconfig
  - Makefile
</FileTree>

What they hold:

- `arch/arm64/configs/` contains ready-made starting configurations (defconfigs) for 64-bit ARM boards.
- `arch/arm64/boot/dts/broadcom/` contains the device tree sources, the hardware lists for Raspberry Pi boards.
- `drivers/` contains all hardware drivers, one directory per kind of device.
- `scripts/` contains build helper scripts, including the `kconfig` tools.
- `init/` contains the code that runs when the kernel starts, including the part that starts the `init` process.
- `mm/`, `fs/` and `net/` contain memory management, the filesystems and networking.

## Understanding Kconfig

<InArticleAd />


The Linux kernel has over 15,000 configuration options, and many depend on others: an SPI driver for one chip is useless if SPI support itself is off. Nobody can keep these rules in their head. If you switch options by hand and break a rule, the build fails, or the kernel builds and then does not boot. The system that records the options and their rules is called **Kconfig**.

Each directory of the kernel source has a `Kconfig` file that declares the options for its part of the kernel (a subsystem): the name, the type, the default and what the option depends on. A simplified entry looks like this:

```kconfig
config SPI
    bool "SPI support"
    help
      The Serial Peripheral Interface (SPI) bus is used to
      communicate with sensors, displays, and other peripherals.
```

The configuration system works with three key files:

| File | Purpose |
|------|---------|
| `Kconfig` | Declares available options, their types, defaults, and dependencies. Distributed throughout the source tree. |
| `.config` | The active configuration file in the build root. Contains all selected options. This is what `make` reads. |
| `defconfig` | A minimal configuration file that records only the options that differ from defaults. Used to create reproducible configurations. |

You never start from nothing. You start from a defconfig that is close to your board, then change it. For the Raspberry Pi Zero 2 W, the closest defconfig is `bcm2711_defconfig`:

```bash
cd ~/rpi-embedded/rpi-linux
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- bcm2711_defconfig
```

This writes a `.config` file with working defaults for Broadcom BCM27xx boards. Keep a copy of it now, because you will compare your changes with it later (`cp .config .config.backup`). Then count its lines:

```bash
wc -l .config
```

You will see roughly 8,000 to 10,000 lines, each representing a configuration choice. Lines starting with `CONFIG_` set a value; lines starting with `# CONFIG_` explicitly disable an option.

Look at a few entries:

```bash
grep CONFIG_SPI .config
grep CONFIG_SOUND .config
grep CONFIG_BT .config
```

<Card title="Why bcm2711_defconfig for a BCM2710?" icon="information">
The BCM2710A1 (Cortex-A53 cores, in the Zero 2 W) and the BCM2711 (Cortex-A72 cores, in the Pi 4) are both 64-bit ARMv8-A chips. The `bcm2711_defconfig` enables the Broadcom peripheral drivers that work on both. The differences between the chips (the type of CPU core, the addresses of the peripherals) are described in the device tree, not in the kernel configuration.
</Card>

## Using menuconfig

<InArticleAd />


You could edit `.config` by hand, but then nothing checks the dependency rules. `menuconfig` is a menu program in the terminal that knows the rules: it shows the options by category, finds an option by name, and shows what each one depends on.

Install the libraries it needs:

```bash
sudo apt install -y libncurses-dev flex bison libssl-dev
```

Launch menuconfig:

```bash
cd ~/rpi-embedded/rpi-linux
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig
```

A blue and gray menu appears in your terminal. These keys control it:

| Key | Action |
|-----|--------|
| Arrow keys | Navigate up/down through menu items |
| Enter | Enter a submenu |
| Space | Toggle an option (cycles through y, m, n) |
| Y | Set to built-in (compiled into the kernel image) |
| M | Set to module (compiled as a loadable .ko file) |
| N | Disable the option entirely |
| / | Search for a config symbol by name |
| ? | Show help text for the highlighted option |
| Esc Esc | Go back (double-press Escape) |

The main menu is organized into top-level categories:

```
  General setup  --->
  Platform selection  --->
  Kernel Features  --->
  Boot options  --->
  Power management options  --->
  CPU Power Management  --->
  [*] Virtualization  --->
  Networking support  --->
  Device Drivers  --->
  File systems  --->
  Security options  --->
  Cryptographic API  --->
  Library routines  --->
```

To find a specific option, press `/` and type the config symbol name (without the `CONFIG_` prefix). For example, searching for `SOUND` will show you where the sound subsystem option lives, what it depends on, and what selects it.

<Card title="Save your configuration" icon="warning">
When you exit menuconfig, it asks if you want to save. Always save. The changes are written to `.config`. Your copy `.config.backup` keeps the starting point, so you can always go back to it.
</Card>

## Stripping the Kernel

<InArticleAd />


Now disable the subsystems your project does not need. Each one you remove means less code to compile, a smaller kernel image, less memory used, and a shorter boot.

For each subsystem below you get its place in the menu and its config symbol. Find it in menuconfig and press N.

### Sound (CONFIG_SOUND)

```
Device Drivers  --->
  <*> Sound card support  --->
```

Press N on "Sound card support" to disable the entire sound subsystem. The Pi Zero 2 W has no onboard audio codec, and our embedded application does not play audio.

### Bluetooth (CONFIG_BT)

```
Networking support  --->
  Bluetooth subsystem support  --->
```

Press N on "Bluetooth subsystem support". Although the Zero 2 W has Bluetooth hardware, we are not using it in this project. You can re-enable it later.

### USB Gadget (CONFIG_USB_GADGET)

```
Device Drivers  --->
  USB support  --->
    USB Gadget Support  --->
```

Press N on "USB Gadget Support". USB Gadget mode lets the Pi act as a USB device (like a serial port or Ethernet adapter when connected to a host). We are using the Pi as a standalone embedded system, so this is not needed.

### Network Filesystems (CONFIG_NETWORK_FILESYSTEMS)

```
File systems  --->
  Network File Systems  --->
```

Press N on "Network File Systems" to disable NFS, CIFS/SMB, and other network-mounted filesystems. Our root filesystem is on the SD card.

### Virtualization (CONFIG_VIRTUALIZATION)

```
Virtualization  --->
```

Press N on the top-level "Virtualization" entry. KVM and other hypervisor support is irrelevant for a 512 MB embedded board.

### Multimedia / V4L2 (CONFIG_MEDIA_SUPPORT)

```
Device Drivers  --->
  Multimedia support  --->
```

Press N on "Multimedia support". This disables the entire Video4Linux2 framework, camera drivers, and TV tuner support.

### Wireless (CONFIG_WLAN)

```
Device Drivers  --->
  Network device support  --->
    Wireless LAN  --->
```

Press N on "Wireless LAN". A system you reach only over the serial console boots faster without wireless drivers. Enable it again when a project needs Wi-Fi, for example to copy files to the board over the network.

### Additional options to disable

You can also turn off these to further reduce size:

```bash
# In menuconfig, search (/) for each symbol and disable:
# CONFIG_STAGING        - experimental drivers
# CONFIG_DRM            - Direct Rendering Manager (GPU/display)
# CONFIG_INPUT_TOUCHSCREEN - touchscreen drivers
# CONFIG_INPUT_JOYSTICK - joystick support
# CONFIG_HID            - Human Interface Device (USB keyboards, mice)
```

After making all these changes, save and exit menuconfig.

Compare your result with the copy you made at the start:

```bash
scripts/diffconfig .config.backup .config
```

This prints a short list of what changed. You should see dozens of options that went from `y` or `m` to `n`. One N in the menu can switch off many options, because everything that depends on a disabled subsystem goes with it.

## Module vs Built-in

<InArticleAd />


A driver does not have to be inside the kernel image. It can also be a module: a separate file on the root filesystem that the running kernel loads when the driver is needed and can remove again. A built-in driver is like a tool you carry in your pocket: ready at once, but carried every day. A module is like a tool on a shelf in the store room: it costs nothing until you go and fetch it. So most driver options have three states:

| Symbol | menuconfig display | Meaning |
|--------|-------------------|---------|
| `y` | `[*]` or `<*>` | **Built-in.** Compiled directly into the kernel image. Available immediately at boot. |
| `m` | `[M]` or `<M>` | **Module.** Compiled as a separate `.ko` file. Must be loaded at runtime with `modprobe` or `insmod`. |
| `n` | `[ ]` or `< >` | **Disabled.** Not compiled at all. |

For an embedded system that must boot fast, the choice follows three rules.

**Drivers needed to boot must be built-in (y).** These are the SD card driver (`CONFIG_MMC`), the filesystem driver (`CONFIG_EXT4_FS`) and the serial console driver (`CONFIG_SERIAL_AMBA_PL011`). The module files are stored on the root filesystem. A kernel that needs a module to read the SD card can never reach that module, like a key locked inside the box it opens.

**Drivers you use only sometimes can be modules (m).** If you sometimes plug in a USB Ethernet adapter, compile its driver as a module. It uses space on the card and no RAM until you load it.

**Drivers you never use should be disabled (n).** This gives the largest gain. A disabled driver is not compiled, not loaded and not started.

For this lesson, set the following to built-in:

```bash
# These should be y (built-in), not m
# Search for each in menuconfig and set to *
CONFIG_MMC=y
CONFIG_MMC_BCM2835=y
CONFIG_EXT4_FS=y
CONFIG_SERIAL_AMBA_PL011=y
CONFIG_I2C=y
CONFIG_I2C_BCM2835=y
CONFIG_SPI=y
CONFIG_SPI_BCM2835=y
CONFIG_GPIO_BCM_VIRT=y
CONFIG_GPIOLIB=y
```

You can also set these directly in `.config` if you prefer not to navigate menuconfig again, but always run `make olddefconfig` afterward to resolve any dependency issues:

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- olddefconfig
```

This command reads `.config` and applies the Kconfig dependency rules. An option whose dependencies are not met is removed, and an option that is newly required gets its default value. Check afterwards with `grep` that the lines you wrote are still there.

## Building the Kernel

<InArticleAd />


The build produces three kinds of files: the kernel image, the loadable modules, and the device tree blobs (the compiled hardware lists).

Set three environment variables so that you do not have to type them in every command:

```bash
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-
export KERNEL_SRC=~/rpi-embedded/rpi-linux
```

Start the build:

```bash
cd $KERNEL_SRC
make -j$(nproc) Image.gz modules dtbs
```

The `-j$(nproc)` flag runs as many parallel compiler processes as your host has CPU cores. On a modern 8-core machine, the full kernel build takes roughly 5 to 15 minutes, depending on how much you disabled.

Each target produces one kind of file:

| Target | Output File | Purpose |
|--------|------------|---------|
| `Image.gz` | `arch/arm64/boot/Image.gz` | Compressed kernel image. The GPU firmware decompresses this into RAM at boot. |
| `Image` | `arch/arm64/boot/Image` | Uncompressed kernel image. Larger but boots slightly faster (no decompression step). |
| `modules` | Various `.ko` files | Loadable kernel modules for any option set to `m`. |
| `dtbs` | `arch/arm64/boot/dts/broadcom/*.dtb` | Device tree blobs. These describe hardware layout to the kernel. |

Verify the build succeeded:

```bash
ls -lh arch/arm64/boot/Image.gz
ls -lh arch/arm64/boot/Image
```

Compare the sizes. `Image.gz` is typically 5 to 8 MB for a stripped kernel, while `Image` might be 15 to 25 MB. We use `Image.gz` to save space on the boot partition and reduce SD card read time.

Check the device tree blob for the Zero 2 W:

```bash
ls -lh arch/arm64/boot/dts/broadcom/bcm2710-rpi-zero-2-w.dtb
```

If you configured any options as modules, you need to collect them:

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
  INSTALL_MOD_PATH=~/rpi-embedded/modules_out modules_install
```

This installs modules into `~/rpi-embedded/modules_out/lib/modules/<kernel-version>/`.

<Card title="Image vs Image.gz" icon="information">
For most embedded projects, `Image.gz` is the better choice. The compressed image is smaller, so it is read from the SD card faster, and unpacking it costs little time. If your storage is fast and every millisecond of boot counts, the uncompressed `Image` removes the unpacking step. In this lesson we use `Image.gz`.
</Card>

## Deploying to the SD Card

<InArticleAd />


Insert the SD card you prepared for the [first boot](/education/embedded-linux-rpi/cross-compilation-boot-process/) and mount both partitions:

```bash
sudo mount /dev/sdX1 /mnt/boot
sudo mount /dev/sdX2 /mnt/rootfs
```

Replace the stock kernel with your custom build:

<Steps>
1. **Back up the existing kernel**

   ```bash
   sudo cp /mnt/boot/kernel8.img /mnt/boot/kernel8.img.stock
   ```

2. **Copy the new kernel image**

   ```bash
   sudo cp $KERNEL_SRC/arch/arm64/boot/Image.gz /mnt/boot/kernel8.img
   ```

   We copy `Image.gz` as `kernel8.img` because that is the filename specified in `config.txt`. The GPU firmware does not care about the actual format; it detects whether the file is compressed or not.

3. **Copy the device tree blob**

   ```bash
   sudo cp $KERNEL_SRC/arch/arm64/boot/dts/broadcom/bcm2710-rpi-zero-2-w.dtb /mnt/boot/
   ```

4. **Copy device tree overlays**

   ```bash
   sudo cp $KERNEL_SRC/arch/arm64/boot/dts/overlays/*.dtb* /mnt/boot/overlays/
   ```

5. **Install kernel modules (if any)**

   ```bash
   sudo mkdir -p /mnt/rootfs/lib/modules
   sudo cp -a ~/rpi-embedded/modules_out/lib/modules/* /mnt/rootfs/lib/modules/
   ```

   Modules are stored in a directory named after the kernel version, and a kernel loads modules only from its own build. So copy them every time you copy a new kernel. If you built everything as built-in, the directory is nearly empty, which is expected.

6. **Unmount and sync**

   ```bash
   sudo umount /mnt/boot
   sudo umount /mnt/rootfs
   sync
   ```
</Steps>

## Measuring Boot Time

<InArticleAd />


To know what you gained, measure it. The kernel can print the time, in seconds since it started, in front of every log message.

Edit `cmdline.txt` on the boot partition to add the `printk.time=1` parameter. Your full `cmdline.txt` should look like:

```
console=serial0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait init=/sbin/init printk.time=1
```

Boot the Pi and capture the serial output. In `picocom`, you can log to a file:

```bash
picocom -b 115200 --logfile boot_log.txt /dev/ttyUSB0
```

After the boot completes, exit picocom (press `Ctrl+A` then `Ctrl+X`) and examine the log. Each line now has a timestamp in seconds:

```
[    0.000000] Booting Linux on physical CPU 0x0000000000 [0x410fd034]
[    0.000000] Linux version 6.6.x ...
...
[    0.512345] mmc0: sdhost-bcm2835 loaded - DMA enabled (>1)
[    1.023456] mmc0: new high speed SDHC card at address 0001
[    1.034567] mmcblk0: mmc0:0001 SD 14.8 GiB
...
[    1.890123] EXT4-fs (mmcblk0p2): mounted filesystem ...
[    1.900000] VFS: Mounted root (ext4 filesystem) ...
...
[    2.100000] Run /sbin/init as init process
```

The timestamp on the "Run /sbin/init" line is the kernel boot time: at that moment the kernel has finished its own start and gives control to the first program. For a stripped kernel it should be well under 3 seconds, against 5 or more seconds with the stock kernel. The time the GPU firmware needs before the kernel starts is not in this number.

On the Pi, the command `dmesg` prints the same log again after boot:

```bash
dmesg | head -5
dmesg | tail -10
```

Find the kernel boot time directly:

```bash
dmesg | grep "Run /sbin/init"
```

To find where the time goes, look for the largest gaps between two messages. The command below takes the timestamp of each line, subtracts the one before it, and sorts the differences:

```bash
# Show the 10 largest time gaps between consecutive messages
dmesg | awk '{print $1}' | tr -d '[]' | awk 'NR>1{printf "%.6f %s\n", $1-prev, $1} {prev=$1}' | sort -rn | head -10
```

Each output line is a gap in seconds and the timestamp where it ends. Look in the log at that timestamp to see which driver was starting. A driver that takes 500 ms and that you do not need is the next one to disable.

<Card title="Comparing before and after" icon="star">
If you measured the boot time of the stock kernel in the first-boot exercises, compare that number with your own kernel. A typical result: the stock kernel reaches init in 4 to 6 seconds, and a stripped kernel in 1.5 to 2.5 seconds. That is two to three times faster from configuration alone, with no change to any code.
</Card>

## Kernel Command Line Parameters

<InArticleAd />


The configuration you just built is fixed inside the kernel image. The kernel command line is for the choices that can change from one boot to the next without a rebuild: where the root filesystem is, where messages go, which program starts first. On the Raspberry Pi it is the text in `cmdline.txt`.

These are the parameters you will use most:

| Parameter | Example | Purpose |
|-----------|---------|---------|
| `console=` | `console=serial0,115200` | Specifies the console device and baud rate. `serial0` is the primary UART on the Pi. You can specify multiple consoles; output goes to all of them. |
| `root=` | `root=/dev/mmcblk0p2` | Tells the kernel which block device contains the root filesystem. `mmcblk0p2` means the second partition of the first MMC (SD card) device. |
| `rootfstype=` | `rootfstype=ext4` | Specifies the filesystem type. Without this, the kernel tries each compiled-in filesystem driver until one works, which is slower. |
| `rootwait` | (no value) | Tells the kernel to wait indefinitely for the root device to appear. Essential for SD cards, which take time to initialize. Without this, the kernel may panic because the card is not ready yet. |
| `init=` | `init=/sbin/init` | Specifies the first userspace process. If omitted, the kernel tries `/sbin/init`, `/etc/init`, `/bin/init`, and `/bin/sh` in order. |
| `printk.time=` | `printk.time=1` | Adds timestamps to kernel log messages. Invaluable for boot time analysis. |
| `quiet` | (no value) | Suppresses most kernel log messages, printing only errors and more severe messages (it sets the console log level to 4). Makes the console output cleaner but hides useful information during development. |
| `loglevel=` | `loglevel=3` | Controls which messages appear on the console: only messages with a level number below this value are printed (0 = emergency, 3 = error, 7 = debug). The default is 7, which shows everything except debug messages. With 3, only critical messages and worse (levels 0 to 2) appear; use 4 if you also want errors. |

You can combine parameters for different scenarios:

<Tabs>
  <TabItem label="Development">
```
console=serial0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait init=/sbin/init printk.time=1 loglevel=7
```
Maximum verbosity. All kernel messages with timestamps. Useful for debugging boot issues.
  </TabItem>
  <TabItem label="Production">
```
console=serial0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait init=/sbin/init quiet loglevel=3
```
Minimal output. Only critical messages and worse reach the console. The `quiet` flag also skips printing the kernel version banner, saving a small amount of boot time.
  </TabItem>
  <TabItem label="Fastest boot">
```
console=serial0,115200 root=/dev/mmcblk0p2 rootfstype=ext4 rootwait init=/bin/hello_linux quiet loglevel=0
```
Skip init entirely and run your application directly as PID 1. The kernel boots, mounts the root filesystem, and immediately executes your binary. This is the fastest possible path to running your code, but your application must handle everything that init normally does (mounting filesystems, etc.). It must also never exit: when PID 1 returns, the kernel panics, so `hello_linux` as written prints its report and then causes a panic. Use this only for single-purpose appliances whose program runs forever.
  </TabItem>
</Tabs>

<Card title="Passing custom parameters" icon="information">
You can also pass arbitrary parameters through `cmdline.txt` that your own init scripts or applications can read. Any parameter that the kernel does not recognize is passed to the init process in its environment. Your application can read these from `/proc/cmdline`. For example, adding `myapp.debug=1` to `cmdline.txt` lets your app check `/proc/cmdline` for this flag.
</Card>

## Saving Your Configuration

<InArticleAd />


Your configuration now exists only as a `.config` file in one folder on one PC. If that file is lost, the work is lost. The `.config` file is also a poor thing to keep: it has thousands of lines, and most of them are defaults. A defconfig stores only the options that differ from the defaults, so it is short and you can read what you changed.

Save your configuration as a defconfig:

```bash
cd $KERNEL_SRC
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- savedefconfig
```

This creates a file called `defconfig` in the kernel build root. Rename and save it:

```bash
cp defconfig arch/arm64/configs/rpi_zero2w_minimal_defconfig
```

Now anyone can produce the same configuration again:

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- rpi_zero2w_minimal_defconfig
```

Embedded Linux teams keep the defconfig in version control and rebuild from it on any machine.
