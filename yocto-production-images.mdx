A customer reports a fault in a device you shipped a year ago, and nobody on the team can build that exact image again: the build PC was replaced, the sources moved on, and nobody recorded which versions went in. The customer also asks which software licenses are inside the device, and a failed update in the field must not leave a device that cannot start. The Yocto Project is the build system most product teams use for these needs. In this lesson you set up a Yocto build for the Raspberry Pi Zero 2 W, put your own software in a layer of its own, write the build instructions (recipes) for the sensor daemon and its client tool, produce a toolchain installer for your team, and lay out the card for updates that can be undone. #YoctoProject #BitBake #ProductionLinux

## What is the Yocto Project?

<InArticleAd />


Buildroot gave you one image from one configuration file. Suppose the product gets a second board. Now there are two configuration files, and every fix must be copied by hand into both. After a year the copies no longer match.

The Yocto Project keeps each concern in a separate place, so that one part can change while the others stay as they are:

- A **recipe** is a file that says how to get, compile and install one piece of software, like the `.mk` file in Buildroot.
- A **layer** is a folder of recipes and settings with one purpose and one owner. The board maker owns the layer for the board, called a BSP (board support package). You own the layer for your applications. For a new board you replace the board layer and keep the rest.
- **BitBake** is the tool that reads every layer and runs the tasks in the right order.

```text
  ┌─────────────────────────────────────┐
  │ meta-siliconwit-rpi (your layer)    │
  │  recipes: sensor-monitord, image    │
  ├─────────────────────────────────────┤
  │ meta-raspberrypi (BSP layer)        │
  │  machine config, bootloader, kernel │
  ├─────────────────────────────────────┤
  │ meta-openembedded (extra packages)  │
  │  libraries, tools, networking       │
  ├─────────────────────────────────────┤
  │ poky (core: meta + meta-poky)       │
  │  gcc, glibc, busybox, systemd       │
  └─────────────────────────────────────┘
```

A layer above can change what a layer below provides. From the four layers BitBake produces the root filesystem, a complete SD card image (a `.wic` file) and the SDK.

<CardGrid>
  <Card title="Core Components" icon="star">
    - **BitBake**: reads the recipes and runs their tasks (fetch, configure, compile, install, package)
    - **OpenEmbedded-Core (OE-Core)**: the base recipes for a minimal Linux system (kernel, glibc, busybox, systemd)
    - **Poky**: the Yocto reference distribution, which is OE-Core with BitBake and a default configuration
    - **Metadata**: recipes (.bb), append files that change a recipe of another layer (.bbappend), configuration (.conf), and classes of shared recipe code (.bbclass)
  </Card>
  <Card title="Yocto vs Buildroot" icon="information">
    - **Buildroot**: Makefile-based, fast first build, one configuration gives one image, good for a small device with one purpose
    - **Yocto**: recipes in layers, an SDK for the team, a list of every license in the image, better for teams and for products that ship in numbers
    - Buildroot compiles everything again after `make clean`. Yocto stores the result of every task in a cache called sstate (shared state), so even a clean build reuses earlier work
  </Card>
</CardGrid>

## Setting Up the Build Environment

<InArticleAd />


The first build downloads and compiles the toolchain and every package. It needs much more disk space and time than Buildroot, so check your PC first.

### Host Requirements

| Resource | Minimum | Recommended |
|----------|---------|-------------|
| Disk space | 50 GB | 100 GB+ |
| RAM | 8 GB | 16 GB+ |
| CPU cores | 4 | 8+ |
| OS | Ubuntu 22.04 LTS | Ubuntu 22.04 LTS |
| First build time | 2 to 4 hours (4 cores) | 1 to 2 hours (8+ cores) |

### Install Dependencies

```bash
sudo apt update
sudo apt install gawk wget git diffstat unzip texinfo gcc build-essential \
    chrpath socat cpio python3 python3-pip python3-pexpect xz-utils \
    debianutils iputils-ping python3-git python3-jinja2 python3-subunit \
    zstd liblz4-tool file locales libacl1
sudo locale-gen en_US.UTF-8
```

### Clone Poky

Clone the Poky repository using the Scarthgap (5.0 LTS) branch:

```bash
mkdir -p ~/yocto && cd ~/yocto
git clone -b scarthgap git://git.yoctoproject.org/poky.git
cd poky
```

### Initialize the Build Environment

```bash
source oe-init-build-env build-rpi
```

This creates a `build-rpi` directory with default configuration files, and lets the shell find the `bitbake` command. The settings last only for this terminal: in every new terminal, source the script again.

The script also moves you into `~/yocto/poky/build-rpi`. You edit the two files in `conf/`: `local.conf` holds the settings of this build, and `bblayers.conf` lists the layers.

  - meta-yocto-bsp/

</FileTree>

## Understanding Layers

<InArticleAd />


By convention a layer's name starts with `meta-`. Each layer has a `conf/layer.conf` that declares its name, its priority, and the Yocto releases it works with.

Layers exist so that you never edit files you do not own. If you change a recipe inside `meta-raspberrypi`, your change is lost or in conflict the next time you update that layer. So each layer has a priority number, and when two layers hold a recipe with the same name, BitBake uses the one from the layer with the higher number. Your layer overrides or appends to a core recipe, and the original stays as its owner wrote it.

### Adding Required Layers

Poky alone does not know the Raspberry Pi. You need two more layers: `meta-raspberrypi`, the BSP for Raspberry Pi boards, and `meta-openembedded` for additional libraries. Clone each on the same release branch as Poky (`scarthgap`): layers of different releases do not work together.

```bash
cd ~/yocto
git clone -b scarthgap git://git.yoctoproject.org/meta-raspberrypi.git
git clone -b scarthgap git://git.openembedded.org/meta-openembedded
```

Add them to the build configuration:

```bash
cd ~/yocto/poky
source oe-init-build-env build-rpi

bitbake-layers add-layer ../../meta-raspberrypi
bitbake-layers add-layer ../../meta-openembedded/meta-oe
bitbake-layers add-layer ../../meta-openembedded/meta-python
bitbake-layers add-layer ../../meta-openembedded/meta-networking
```

Verify the layer configuration:

```bash
bitbake-layers show-layers
```

Expected output:

```
layer                 path                                      priority
==========================================================================
meta                  /home/user/yocto/poky/meta                5
meta-poky             /home/user/yocto/poky/meta-poky           5
meta-yocto-bsp        /home/user/yocto/poky/meta-yocto-bsp      5
meta-raspberrypi      /home/user/yocto/meta-raspberrypi          9
meta-oe               /home/user/yocto/meta-openembedded/meta-oe 6
meta-python           /home/user/yocto/meta-openembedded/meta-python 7
meta-networking       /home/user/yocto/meta-openembedded/meta-networking 5
```

The `bblayers.conf` file records the layer list:

```bash title="conf/bblayers.conf"
BBLAYERS ?= " \
  /home/user/yocto/poky/meta \
  /home/user/yocto/poky/meta-poky \
  /home/user/yocto/poky/meta-yocto-bsp \
  /home/user/yocto/meta-raspberrypi \
  /home/user/yocto/meta-openembedded/meta-oe \
  /home/user/yocto/meta-openembedded/meta-python \
  /home/user/yocto/meta-openembedded/meta-networking \
"
```

## Creating Your Custom Layer

<InArticleAd />


Everything that is yours goes into one layer of your own: the application recipes, the definition of the image, and your settings.

```bash
cd ~/yocto/poky
source oe-init-build-env build-rpi

bitbake-layers create-layer ../../meta-siliconwit-rpi
bitbake-layers add-layer ../../meta-siliconwit-rpi
```

Populate the layer with the directories you need:

```bash
cd ~/yocto/meta-siliconwit-rpi
mkdir -p recipes-apps/sensor-monitord/files
mkdir -p recipes-apps/sensor-query/files
mkdir -p recipes-core/images
mkdir -p conf/distro
mkdir -p wic
```

The full layer structure:

<FileTree>
- meta-siliconwit-rpi/
  - conf/
    - layer.conf
    - distro/
      - siliconwit-rpi.conf
  - recipes-apps/
    - sensor-monitord/
      - sensor-monitord_1.0.bb
      - files/
        - sensor-monitord.c
        - sensor-protocol.h
        - sensor-monitord.service
    - sensor-query/
      - sensor-query_1.0.bb
      - files/
        - sensor-query.c
        - sensor-protocol.h
  - recipes-core/
    - images/
      - siliconwit-image-sensor.bb
  - wic/
    - siliconwit-rpi-ab.wks
  - COPYING.MIT
  - README
</FileTree>

Edit the layer configuration:

```python title="conf/layer.conf"
# Layer configuration for meta-siliconwit-rpi
BBPATH .= ":${LAYERDIR}"

BBFILES += " \
    ${LAYERDIR}/recipes-*/*/*.bb \
    ${LAYERDIR}/recipes-*/*/*.bbappend \
"

BBFILE_COLLECTIONS += "siliconwit-rpi"
BBFILE_PATTERN_siliconwit-rpi = "^${LAYERDIR}/"
BBFILE_PRIORITY_siliconwit-rpi = "10"

LAYERDEPENDS_siliconwit-rpi = "core raspberrypi"
LAYERSERIES_COMPAT_siliconwit-rpi = "scarthgap"
```

The priority of 10 is higher than that of every other layer in the list above, so your recipe is used when two recipes have the same name. `LAYERDEPENDS` uses collection names, not directory names: the collection that `meta-raspberrypi` declares in its own `layer.conf` is `raspberrypi`.

## Writing Application Recipes

<InArticleAd />


A recipe file is named `<name>_<version>.bb`.

### sensor-monitord Recipe

Read the recipe in three parts. The top says what the software is and under which license. The middle says where the source files are and what the software needs. The two functions at the end, `do_compile()` and `do_install()`, are the commands you would type by hand. Each `${...}` is a BitBake variable: `${CC}` is the cross-compiler, `${D}` is a temporary folder that stands for `/` on the target, and `${PN}` is the name of the package.

```python title="recipes-apps/sensor-monitord/sensor-monitord_1.0.bb"
SUMMARY = "BME280 sensor monitoring daemon with systemd integration"
DESCRIPTION = "Reads BME280 temperature, pressure, and humidity data \
via I2C, stores readings in shared memory, serves clients over a Unix \
domain socket, and integrates with systemd watchdog and journald."
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = " \
    file://sensor-monitord.c \
    file://sensor-protocol.h \
    file://sensor-monitord.service \
"

S = "${WORKDIR}"

DEPENDS = "systemd"
RDEPENDS:${PN} = "i2c-tools"

inherit systemd

SYSTEMD_SERVICE:${PN} = "sensor-monitord.service"
SYSTEMD_AUTO_ENABLE = "enable"

do_compile() {
    ${CC} ${CFLAGS} ${LDFLAGS} -o sensor-monitord sensor-monitord.c \
        -lrt -lpthread -lsystemd -lm
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 sensor-monitord ${D}${bindir}/sensor-monitord

    install -d ${D}${systemd_system_unitdir}
    install -m 0644 sensor-monitord.service ${D}${systemd_system_unitdir}/sensor-monitord.service

    # The unit file from Lesson 7 starts /usr/local/bin/sensor-monitord,
    # but this recipe installs the binary in ${bindir} (/usr/bin)
    sed -i -e 's|/usr/local/bin|${bindir}|' \
        ${D}${systemd_system_unitdir}/sensor-monitord.service
}

FILES:${PN} = " \
    ${bindir}/sensor-monitord \
    ${systemd_system_unitdir}/sensor-monitord.service \
"
```

The other variables:

| Element | Purpose |
|---------|---------|
| `LICENSE` and `LIC_FILES_CHKSUM` | The license, and a checksum of its text so BitBake can detect a changed license. Required for every recipe |
| `SRC_URI` | Source files to fetch. `file://` means local files in the `files/` subdirectory next to the recipe |
| `S = "${WORKDIR}"` | Source directory. Local files, not an archive, are directly in WORKDIR |
| `DEPENDS` | Needed to compile: here the systemd headers and libraries |
| `RDEPENDS:${PN}` | Needed on the device with this package. i2c-tools puts `i2cdetect` and related tools on the target for checking the bus; the I2C kernel modules are loaded by `KERNEL_MODULE_AUTOLOAD` in `local.conf` |
| `inherit systemd` and `SYSTEMD_SERVICE:${PN}` | The systemd class enables the named service at boot |
| `FILES:${PN}` | Which installed files belong to the main package |

Copy the source files of the daemon you built in the [system services lesson](/education/embedded-linux-rpi/system-services-process-management/) into the recipe's `files/` directory:

```bash
cp ~/rpi-sensor-daemon/src/sensor-monitord.c \
   ~/yocto/meta-siliconwit-rpi/recipes-apps/sensor-monitord/files/

cp ~/rpi-sensor-daemon/src/sensor-protocol.h \
   ~/yocto/meta-siliconwit-rpi/recipes-apps/sensor-monitord/files/

cp ~/rpi-sensor-daemon/systemd/sensor-monitord.service \
   ~/yocto/meta-siliconwit-rpi/recipes-apps/sensor-monitord/files/
```

### sensor-query Recipe

The client tool needs no service file and no systemd library, so its recipe is the same pattern with fewer lines.

```python title="recipes-apps/sensor-query/sensor-query_1.0.bb"
SUMMARY = "Client tool for sensor-monitord"
DESCRIPTION = "Command-line client that queries the sensor monitoring \
daemon over a Unix domain socket."
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = " \
    file://sensor-query.c \
    file://sensor-protocol.h \
"

S = "${WORKDIR}"

do_compile() {
    ${CC} ${CFLAGS} ${LDFLAGS} -o sensor-query sensor-query.c -lrt
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 sensor-query ${D}${bindir}/sensor-query
}

FILES:${PN} = "${bindir}/sensor-query"
```

Copy the source files:

```bash
cp ~/rpi-sensor-daemon/src/sensor-query.c \
   ~/yocto/meta-siliconwit-rpi/recipes-apps/sensor-query/files/

cp ~/rpi-sensor-daemon/src/sensor-protocol.h \

```

### Verifying Recipes Parse Correctly

A full build takes hours, so find mistakes in the recipes first. `bitbake -e` prints every variable of a recipe after BitBake has read (parsed) all the layers:

```bash
cd ~/yocto/poky
source oe-init-build-env build-rpi

bitbake -e sensor-monitord | grep ^SRC_URI=
bitbake -e sensor-query | grep ^SRC_URI=
```

On a parse error BitBake prints the file and line number. The usual causes are a missing backslash in a variable of several lines, and wrong indentation.

## The Image Recipe

<InArticleAd />


An image recipe builds no software. It is the list of packages that go into the root filesystem, like the package choices in the Buildroot menu. It inherits the `core-image` class, which gives a minimal system that starts, and adds your packages to it.

```python title="recipes-core/images/siliconwit-image-sensor.bb"
SUMMARY = "SiliconWit Sensor Image for Raspberry Pi Zero 2 W"
DESCRIPTION = "Production image with BME280 sensor daemon, client tool, \
systemd integration, and essential networking utilities."
LICENSE = "MIT"

inherit core-image

# Base system features
IMAGE_FEATURES += " \
    ssh-server-dropbear \
    package-management \
"

# Application packages
IMAGE_INSTALL += " \
    sensor-monitord \
    sensor-query \
"

# System utilities
IMAGE_INSTALL += " \
    i2c-tools \
    systemd-analyze \
    htop \
    nano \
    socat \
"

# Networking
IMAGE_INSTALL += " \
    openssh-sftp-server \
    wpa-supplicant \
    dhcpcd \
    ntp \
"

# Kernel modules for I2C
IMAGE_INSTALL += " \
    kernel-module-i2c-bcm2835 \
    kernel-module-i2c-dev \
"

# Set root password (change for production)
EXTRA_IMAGE_FEATURES += "debug-tweaks"

# Image size settings
IMAGE_ROOTFS_EXTRA_SPACE = "131072"
```

Key points:

- `ssh-server-dropbear` installs a small SSH server so you can reach the board over the network.
- `debug-tweaks` sets an empty root password and allows root login. With it, anyone on the network can enter the device. Remove it before an image leaves your bench.
- `IMAGE_ROOTFS_EXTRA_SPACE` adds 128 MB (the value is in KB) of free space beyond what the packages need.
- Each `IMAGE_INSTALL` entry must be a recipe or package that BitBake can find in the layers.

## Machine and Distro Configuration

<InArticleAd />


Yocto separates two questions. The machine is the hardware: which processor, kernel and device tree. The distro is the policy for the whole system: which init system and which features. With the two apart, one distro can run on several machines.

### Machine Configuration (local.conf)

Edit `conf/local.conf` in your build directory to target the Raspberry Pi Zero 2 W:

```bash title="conf/local.conf (key settings)"
# Target machine
MACHINE = "raspberrypi0-2w-64"

# Use systemd as the init manager
DISTRO_FEATURES:append = " systemd"
DISTRO_FEATURES_BACKFILL_CONSIDERED:append = " sysvinit"
VIRTUAL-RUNTIME_init_manager = "systemd"
VIRTUAL-RUNTIME_initscripts = "systemd-compat-units"

# Enable I2C
ENABLE_I2C = "1"
KERNEL_MODULE_AUTOLOAD:rpi += "i2c-dev i2c-bcm2835"

# Enable UART for serial console debugging
ENABLE_UART = "1"

# WiFi firmware
MACHINE_EXTRA_RRECOMMENDS += "linux-firmware-rpidistro-bcm43436s"

# Use RPi kernel
PREFERRED_PROVIDER_virtual/kernel = "linux-raspberrypi"

# Parallel build settings (adjust to your host)
BB_NUMBER_THREADS = "8"
PARALLEL_MAKE = "-j 8"

# Download and shared-state cache directories
DL_DIR = "${TOPDIR}/../downloads"
SSTATE_DIR = "${TOPDIR}/../sstate-cache"
```

`MACHINE` is the most important setting. It selects the BSP recipes, the kernel configuration and the device tree files. The `raspberrypi0-2w-64` definition comes from the `meta-raspberrypi` layer and is 64-bit (AArch64).

### Custom Distro Configuration (Optional)

For production, you may want a distro of your own that starts from the Poky defaults and changes some of them:

```python title="conf/distro/siliconwit-rpi.conf"
require conf/distro/poky.conf

DISTRO = "siliconwit-rpi"
DISTRO_NAME = "SiliconWit RPi Distribution"
DISTRO_VERSION = "1.0"

# Strip down DISTRO_FEATURES for an embedded target
DISTRO_FEATURES = "acl ipv4 ipv6 systemd usbhost wifi largefile pam"

# Use systemd everywhere
VIRTUAL-RUNTIME_init_manager = "systemd"
VIRTUAL-RUNTIME_initscripts = "systemd-compat-units"
VIRTUAL-RUNTIME_login_manager = "shadow-base"
VIRTUAL-RUNTIME_dev_manager = "systemd"

# Default timezone
DEFAULT_TIMEZONE = "UTC"

# Optimize for size
FULL_OPTIMIZATION = "-O2 -pipe"
```

To use this distro, set `DISTRO = "siliconwit-rpi"` in `local.conf`. If you skip this step, the default Poky distro is enough for development.

## Building the Image

<InArticleAd />


With all layers, recipes, and configuration in place, build the image:

```bash
cd ~/yocto/poky
source oe-init-build-env build-rpi

bitbake siliconwit-image-sensor
```

### Build Stages

BitBake takes each of the hundreds of recipes through the same tasks. When a build fails, the error names a recipe and one of these tasks, and that tells you where to look:

| Task | Description |
|------|-------------|
| `do_fetch` | Download source code from SRC_URI (tarballs, git repos, local files) |
| `do_unpack` | Extract archives into the work directory |
| `do_patch` | Apply any patches listed in SRC_URI |
| `do_configure` | Run configure scripts (autotools, cmake, etc.) |
| `do_compile` | Compile the source code using the cross-toolchain |
| `do_install` | Install built files into a staging directory |
| `do_package` | Split installed files into packages (rpm, deb, or ipk) |
| `do_rootfs` | (Image only) Assemble all packages into the root filesystem |
| `do_image` | (Image only) Generate the final image files (ext4, wic, etc.) |

Monitor the build progress:

```bash
# In another terminal, watch the build log
tail -f ~/yocto/poky/build-rpi/tmp/log/cooker/raspberrypi0-2w-64/*.log
```

The first build takes 1 to 3 hours, depending on your PC. Later builds are much faster, because BitBake keeps the result of each task in the sstate cache and runs a task again only when its inputs have changed.

### Build Output

After a successful build, the output images are in:

```bash
ls tmp/deploy/images/raspberrypi0-2w-64/
```

Key output files:

| File | Description |
|------|-------------|
| `siliconwit-image-sensor-raspberrypi0-2w-64.rootfs.wic.bz2` | Complete SD card image (boot + rootfs) |
| `siliconwit-image-sensor-raspberrypi0-2w-64.rootfs.ext4` | Root filesystem only |
| `Image` | Kernel image |
| `bcm2710-rpi-zero-2-w.dtb` | Device tree blob |
| `siliconwit-image-sensor-raspberrypi0-2w-64.rootfs.manifest` | List of all installed packages |

### Writing to an SD Card

```bash
cd tmp/deploy/images/raspberrypi0-2w-64/

# Decompress the image
bzip2 -dk siliconwit-image-sensor-raspberrypi0-2w-64.rootfs.wic.bz2

# Write to SD card (replace /dev/sdX with your actual device)
sudo dd if=siliconwit-image-sensor-raspberrypi0-2w-64.rootfs.wic \
    of=/dev/sdX bs=4M status=progress conv=fsync
```

<Card title="Double-check the target device" icon="warning">
The `dd` command writes raw data to a block device. Writing to the wrong device will destroy data. Use `lsblk` to identify your SD card before running `dd`. The SD card is typically `/dev/sdb` or `/dev/mmcblk0`.
</Card>

## SDK Generation

<InArticleAd />


An application developer should not need 50 GB of disk and a build of several hours to compile one C file. A compiler from elsewhere is no answer: its C library may differ from the one in your image. The SDK (software development kit) is one installer file made from your image. It holds the cross-compiler, the sysroot (a copy of the libraries and headers of the target), and a script that sets the environment.

### Building the SDK

```bash
bitbake -c populate_sdk siliconwit-image-sensor
```

This produces an SDK installer script in `tmp/deploy/sdk/`:

```bash
ls tmp/deploy/sdk/
```

The output is a self-extracting shell script, for example:

```
poky-glibc-x86_64-siliconwit-image-sensor-cortexa53-raspberrypi0-2w-64-toolchain-5.0.sh
```

### Installing and Using the SDK

```bash
# Install to the default location (/opt/poky/5.0)
```

## A/B Root Filesystem for OTA

<InArticleAd />


A device in the field is updated over the network, with nobody near it. If the update writes over the running system and the power fails halfway, the device holds half an old system and half a new one, and it cannot start.

The A/B method removes that risk. The card holds two root filesystem partitions, called slots. The device runs from one slot, and an update is written to the other. Only when the write is complete is the bootloader told to start from the new slot. If the new system does not start, the bootloader returns to the old slot, which nobody has touched. It is like building a new bridge beside the old one: traffic uses the old bridge until the new one is complete and tested.

### Partition Layout

```text
  ┌──────────────────────────────────────┐
  │ boot (FAT32, 64 MB)                  │
  │  kernel, DTBs, config.txt, U-Boot    │
  ├──────────────────────────────────────┤
  │ rootfsA (ext4, 512 MB) ◄── active    │
  │  current running system              │
  ├──────────────────────────────────────┤
  │ rootfsB (ext4, 512 MB) ◄── standby   │
  │  OTA writes new image here           │
  ├──────────────────────────────────────┤
  │ data (ext4, 256 MB in the image)     │
  │  kept: logs, config, database        │
  └──────────────────────────────────────┘
```

The safety has a price: the card holds the root filesystem twice. The data partition is mounted at `/data`. It is 256 MB in the image file, and you grow it on first boot to fill the card.

### WKS File for SD Card Layout

Yocto builds the card image with a tool named WIC, which reads the partition layout from a `.wks` file. Each `part` line is one partition, in the order of the drawing, with sizes in MB. Create a custom WKS file:

```bash title="wic/siliconwit-rpi-ab.wks"
# Boot partition (FAT32)
part /boot --source bootimg-partition --ondisk mmcblk0 \
    --fstype=vfat --label boot --active --align 4096 --size 64

# Root filesystem A
part / --source rootfs --ondisk mmcblk0 \
    --fstype=ext4 --label rootfsA --align 4096 --size 512

# Root filesystem B (initially empty, same size as A)
part --ondisk mmcblk0 \
    --fstype=ext4 --label rootfsB --align 4096 --size 512

# Persistent data partition (256 MB in the image; wic cannot fill the
# card, so grow this partition on first boot)
part /data --ondisk mmcblk0 \
    --fstype=ext4 --label data --align 4096 --size 256
```

To use this layout, add the following to `local.conf`:

```bash
WKS_FILE = "siliconwit-rpi-ab.wks"
IMAGE_FSTYPES = "wic.bz2 ext4"
```

### U-Boot Environment for A/B Switching

Something must choose the slot before Linux starts. By default the `meta-raspberrypi` layer lets the Pi firmware start the kernel directly. U-Boot is a bootloader that can run small scripts. To put it between the firmware and the kernel, add `RPI_USE_U_BOOT = "1"` to `local.conf`.

U-Boot keeps named values, its environment, on the card. Below, `boot_slot` selects the slot, `select_root` turns it into a partition number, and `boot_kernel` passes that partition to the kernel as `root=`:

```bash title="u-boot-env.txt"
# A/B boot selection
# boot_slot: 0 = rootfsA (mmcblk0p2), 1 = rootfsB (mmcblk0p3)
boot_slot=0
boot_attempts=0
max_boot_attempts=3

bootcmd=run select_root; run boot_kernel

select_root=if test ${boot_slot} -eq 0; then setenv root_part 2; setenv root_label rootfsA; else setenv root_part 3; setenv root_label rootfsB; fi

boot_kernel=setenv bootargs "console=ttyS0,115200 root=/dev/mmcblk0p${root_part} rootfstype=ext4 rootwait"; fatload mmc 0:1 ${kernel_addr_r} Image; fatload mmc 0:1 ${fdt_addr} bcm2710-rpi-zero-2-w.dtb; booti ${kernel_addr_r} - ${fdt_addr}
```

### The OTA Update Flow

<Steps>

1. **Write the new image to the inactive partition**

   If the device now runs from rootfsA (partition 2), the update writes to rootfsB (partition 3). The commands `fw_printenv` and `fw_setenv` read and write the U-Boot environment from Linux:

   ```bash
   # Determine the inactive partition
   CURRENT=$(fw_printenv -n boot_slot)
   if [ "$CURRENT" = "0" ]; then
       TARGET_DEV="/dev/mmcblk0p3"
       NEW_SLOT=1
   else
       TARGET_DEV="/dev/mmcblk0p2"
       NEW_SLOT=0
   fi

   # Write the new rootfs image
   dd if=/tmp/new-rootfs.ext4 of=$TARGET_DEV bs=4M conv=fsync
   ```

2. **Switch the boot flag**

   ```bash
   fw_setenv boot_slot $NEW_SLOT
   fw_setenv boot_attempts 0
   ```

3. **Reboot into the new partition**

   ```bash
   reboot
   ```

4. **Verify and finalize (in the new root)**

   After the reboot, the application runs a self-test. If the test passes, it marks the update as good. If the boot or the self-test fails, U-Boot adds one to `boot_attempts`. After `max_boot_attempts` failures, U-Boot returns to the previous partition. The environment above does not yet contain this counting step. You add it yourself:

   ```bash
   # Add this to the U-Boot bootcmd (before boot_kernel):
   # if boot_attempts > max_boot_attempts, swap boot_slot back
   ```

</Steps>

Both root filesystems use the same data partition (`/data`), and an update never writes to it. Store application configuration, sensor logs, and calibration data there.

## Reproducible Builds

<InArticleAd />


A reproducible build gives the same image whenever and wherever you run it from the same inputs. Without it you cannot answer the question "which exact code is running on that device?".

The commands so far are not reproducible. `git clone -b scarthgap` takes the newest commit of a branch, and the branch receives fixes every week.

### Locking Layer Revisions with kas

[kas](https://kas.readthedocs.io/) is a setup tool that names every layer, its exact git commit, and the build settings in one YAML file. The commit values below are placeholders: put the real commit hashes of your clones there (`git rev-parse HEAD` in each layer).

```yaml title="kas-siliconwit.yml"
header:
  version: 14

machine: raspberrypi0-2w-64
distro: poky

repos:
  poky:
    url: "git://git.yoctoproject.org/poky.git"
    branch: scarthgap
    commit: "a1b2c3d4e5f6..."
    layers:
      meta:
      meta-poky:

  meta-raspberrypi:
    url: "git://git.yoctoproject.org/meta-raspberrypi.git"
    branch: scarthgap
    commit: "f6e5d4c3b2a1..."

  meta-openembedded:
    url: "git://git.openembedded.org/meta-openembedded"
    branch: scarthgap
    commit: "1a2b3c4d5e6f..."
    layers:
      meta-oe:
      meta-python:
      meta-networking:

  meta-siliconwit-rpi:
    path: "../meta-siliconwit-rpi"

local_conf_header:
  siliconwit: |
    DISTRO_FEATURES:append = " systemd"
    DISTRO_FEATURES_BACKFILL_CONSIDERED:append = " sysvinit"
    VIRTUAL-RUNTIME_init_manager = "systemd"
    VIRTUAL-RUNTIME_initscripts = "systemd-compat-units"
    ENABLE_I2C = "1"
    ENABLE_UART = "1"
    KERNEL_MODULE_AUTOLOAD:rpi += "i2c-dev i2c-bcm2835"

target: siliconwit-image-sensor
```

Build with kas:

```bash
pip3 install kas
kas build kas-siliconwit.yml
```

kas checks out the exact commit named for each layer, generates `local.conf` and `bblayers.conf`, and runs BitBake. Anyone with this YAML file and your layer can build the same image.

### Sharing the Shared State Cache (SSTATE)

The sstate cache stores the output of each task under a hash of everything that went into it. If the hash matches, the stored output is used and nothing is compiled. When developers and the build server share one cache, each piece is compiled once for the whole team.

Set up a shared cache on a network drive or HTTP server:

```bash
# In local.conf, point to a shared directory
SSTATE_DIR = "/shared/yocto/sstate-cache"
DL_DIR = "/shared/yocto/downloads"

# Or use an HTTP mirror for read-only access
SSTATE_MIRRORS = "file://.* http://sstate-server.local/sstate/PATH"
```

With a filled sstate cache, a rebuild that changes only one recipe takes minutes, not hours.

### Building in a Container

The layers are now locked, but the build PC is not: a different Ubuntu version brings different host tools. Run the build inside a Docker container (a packaged, fixed copy of an operating system) so that every build uses the same host:

```dockerfile title="Dockerfile"
FROM ubuntu:22.04

RUN apt-get update && apt-get install -y \
    gawk wget git diffstat unzip texinfo gcc build-essential \
    chrpath socat cpio python3 python3-pip python3-pexpect \
    xz-utils debianutils iputils-ping python3-git python3-jinja2 \
    python3-subunit zstd liblz4-tool file locales libacl1 \
    && locale-gen en_US.UTF-8

ENV LANG=en_US.UTF-8

RUN useradd -m builder
USER builder
WORKDIR /home/builder

CMD ["/bin/bash"]
```

Build and run:

```bash
docker build -t yocto-builder .
docker run -it -v ~/yocto:/home/builder/yocto yocto-builder
```

Inside the container, follow the same steps: source the environment, run BitBake.

## License Compliance

<InArticleAd />


Every open-source component in your image has a license with conditions for shipping it. Some ask only that you include their text. The GPL family also asks that you offer the source code. An image holds hundreds of components, so a list made by hand will miss some. Yocto makes the list from the `LICENSE` line of every recipe.

### Generating the License Manifest

After building the image, generate a complete license manifest:

```bash
bitbake -c populate_lic siliconwit-image-sensor
```

The output is in `tmp/deploy/licenses/siliconwit-image-sensor-raspberrypi0-2w-64/`:

```bash
ls tmp/deploy/licenses/siliconwit-image-sensor-raspberrypi0-2w-64/
```

This directory contains:

- `license.manifest`: a text file listing every package, its version, and its license
- Individual directories for each package containing the actual license text files

### Understanding SPDX

Yocto names licenses with SPDX (Software Package Data Exchange) identifiers, a standard set of short names such as `MIT`, `Apache-2.0`, `BSD-3-Clause`, `GPL-2.0-only` and `LGPL-2.1-only`. The ending `-only` or `-or-later` says whether later versions of the license also apply.

### Handling Commercial Licenses

Some packages have terms that may need a paid license in a product. BitBake refuses to build them until you accept them by name:

```bash
# In local.conf, allow specific commercial licenses
LICENSE_FLAGS_ACCEPTED = "commercial"
```

For production, be more specific about which commercial packages you accept:

```bash
LICENSE_FLAGS_ACCEPTED = "commercial_ffmpeg commercial_x264"
```

### License Auditing Workflow

<Steps>

1. **Build the image and generate the manifest**

   ```bash
   bitbake siliconwit-image-sensor
   ```

2. **Review the license manifest**

   ```bash
   cat tmp/deploy/licenses/siliconwit-image-sensor-raspberrypi0-2w-64/license.manifest
   ```

   Check for any unexpected licenses (especially GPL in a proprietary product).

3. **Generate source archives for GPL compliance**

   GPL licenses require that you provide the corresponding source code. Yocto can archive all sources:

   ```bash
   # Add to local.conf
   INHERIT += "archiver"
   ARCHIVER_MODE[src] = "original"
   ```

   Rebuild, and source tarballs appear in `tmp/deploy/sources/`.

4. **Include the license manifest in your product documentation**

   Many products ship a "Third-Party Software Notices" document generated from this manifest.

</Steps>
